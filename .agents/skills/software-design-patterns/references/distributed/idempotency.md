# 幂等模式（Idempotency）

**类别：** 分布式系统模式

## 意图

确保同一业务操作重复提交或重复消费不会产生额外副作用。

## 什么时候使用

- 网络重试、消息至少一次投递、支付/下单重复请求。
- 客户端可能因超时不确定结果而重试。
- Saga/Outbox 消费者需要去重。

## 什么时候不要使用

- 纯读操作天然幂等无需额外机制。
- 用随机延迟掩盖重复问题。

## 识别信号

- Idempotency-Key
- dedup table
- 重复消息

## 实现要点

- 选择稳定业务幂等键。
- 持久化处理结果或去重记录。
- 定义幂等记录 TTL 与并发竞争策略。

## 常见误用

- 仅在内存去重，重启失效。
- 用请求 body hash 但忽略业务语义。
- 先执行副作用再写幂等记录产生竞态。

## 常见组合

- Retry
- Outbox
- Saga

## 最小示意

```text
if processed(key): return previousResult; else atomically process+record
```

## 深度分析

### 变化压力
幂等性处理的是客户端超时重试、消息至少一次投递和并发重复请求导致的额外副作用。它要求定义“同一个业务意图”的稳定键，而不是简单对 body 做 hash。

### 结构与协作
入口提取 Idempotency-Key/业务键，与请求者或租户绑定；在持久化层原子地 claim、执行和记录结果，重复请求返回相同结果或明确处理中状态。消息消费者以 eventId 或业务键去重，TTL、冲突和结果保留策略要与业务结算周期匹配。

### 关键权衡与替代
持久化去重增加存储、锁和结果回放成本，但比重复扣款/创建更安全。天然幂等读无需额外表；非幂等写若不能提供业务键，应先改 API 契约。幂等不等于 exactly-once，外部副作用仍需供应商幂等能力。

### 落地与验证
先覆盖一个可重试写端点，定义 key 格式、作用域、参数不一致错误和过期策略。测试并发 claim、进程崩溃恢复、重复返回、键复用冲突和消息重放；监控 duplicate rate、claim contention、store latency。记录 key 的摘要，不记录敏感请求体。

## 退出条件

当操作天然幂等或已由下游提供同等强度的业务去重时，删除重复存储，保留契约级说明。
