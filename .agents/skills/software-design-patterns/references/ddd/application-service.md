# 应用服务模式（Application Service）

**类别：** DDD 模式

## 意图

实现单个应用用例的编排：鉴权、事务、加载聚合、调用领域行为、保存、发布事件。

## 什么时候使用

- 需要清晰用例边界。
- 多个传输入口共享同一业务流程。
- DDD 中要隔离应用编排与领域规则。

## 什么时候不要使用

- 把核心计算、状态规则全部塞进 Application Service。
- 非常简单的应用为每个一行操作创建巨大层次。

## 识别信号

- Use case handler
- Command handler
- 事务编排

## 实现要点

- 一个方法对应一个明确用例。
- 领域规则委托给实体/值对象/领域服务。
- 基础设施通过端口/仓储注入。

## 常见误用

- 胖应用服务。
- 直接 set 实体字段。
- 跨多个微服务开启伪分布式事务。

## 常见组合

- Repository
- Domain Service
- Domain Event
- Unit of Work

## 最小示意

```text
PayOrder.handle(cmd): load -> order.pay() -> save -> publish events
```

## 深度分析

### 变化压力
当 HTTP、消息和 CLI 都要执行同一个用例，且每个入口各自加载、鉴权、提交或发布事件时，应用服务提供统一的用例边界。它编排流程，不拥有核心业务规则。

### 结构与协作
入口适配器把 DTO 转成命令；Application Service 依次完成授权、输入校验、开启 UoW、加载聚合、调用领域行为、提交并发布事件。依赖通过端口注入，返回稳定结果/错误映射给适配器。一个公开方法最好对应一个可追踪用例。

### 关键权衡与替代
收益是流程一致、事务和错误责任清楚；代价是会增加一层调用。若只有一个入口和一行 CRUD，直接 handler 更简单。与 Service Layer 的边界是：Application Service 面向用例并调用领域行为，Service Layer 是更宽的应用分层概念，不应两者重复包装。

### 落地与验证
先把重复入口收敛到一个用例方法，再抽出纯领域规则。测试从命令进入到最终提交/响应，覆盖鉴权失败、领域拒绝、事务回滚和事件发布；日志带 useCase、correlationId、aggregateId。若服务方法持续增长，按用例拆分而不是继续加 Options。

## 退出条件

当服务只做一比一转发且没有事务、授权或多入口复用时，删除该层或合并到入口适配器。
