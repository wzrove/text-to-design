# DDD 工厂模式（DDD Factory）

**类别：** DDD 模式

## 意图

把具有领域约束的复杂聚合/实体创建封装在领域工厂中，确保一出生即有效。

## 什么时候使用

- 创建对象需要多步规则、多个值对象或领域服务。
- 构造逻辑本身具有领域含义。
- 不同创建路径必须共享不变量。

## 什么时候不要使用

- 普通构造器已经足够清楚。
- 只是基础设施对象装配，应使用 DI/Factory Method。

## 识别信号

- 复杂聚合创建
- 构造参数来自多个来源
- 创建时需领域校验

## 实现要点

- Factory 返回完整有效领域对象。
- 使用领域语言命名 create/open/register。
- 不要让工厂承担后续生命周期业务。

## 常见误用

- 所有 new 都必须过 Factory。
- 工厂偷偷访问数据库和远程服务导致不可测试。

## 常见组合

- Aggregate
- Value Object
- Factory Method

## 最小示意

```text
order = OrderFactory.create(customer, lines, pricingPolicy)
```

## 深度分析

### 变化压力
领域工厂只解决“创建本身包含领域知识且必须一出生即有效”的问题，例如多种创建路径共享货币、额度和初始状态规则。它不是所有 new 的统一入口。

### 结构与协作
工厂输入原始命令、值对象或已解析的策略，内部创建值对象、计算默认值并调用聚合构造器，成功时返回完整有效对象，失败返回领域错误。数据库查找、远程调用和依赖装配留给应用层或基础设施。

### 关键权衡与替代
工厂集中不变量，代价是增加命名和测试面。简单构造使用构造器/命名参数；按类型选择实现使用 Factory Method；分阶段可选参数使用 Builder。若工厂需要读取当前库存或调用支付服务，那是应用服务编排，不应继续膨胀工厂。

### 落地与验证
先画出所有创建路径的共同不变量，再让工厂覆盖一个入口，保留旧构造器作为迁移适配。测试每个创建路径的有效对象、拒绝原因和默认值版本；记录 factoryPath 和 domainRuleVersion。确认重放/导入场景不会误触发创建副作用。

## 退出条件

当工厂只包一行构造器或创建路径稳定为一条时，删除工厂并保留直接构造。
