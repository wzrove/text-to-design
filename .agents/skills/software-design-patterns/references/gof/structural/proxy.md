# 代理模式（Proxy）

**类别：** GoF / 结构型

## 意图

用替身控制对真实对象的访问，可实现权限、延迟加载、远程调用、事务等横切能力。

## 什么时候使用

- 需要访问控制、事务边界、远程代理、懒加载。
- 调用方应保持与真实对象相同接口。
- AOP/动态代理能透明施加横切逻辑。

## 什么时候不要使用

- 只是想叠加可选功能，Decorator 更合适。
- 横切逻辑依赖大量业务细节，透明代理会让行为难预测。
- 内部自调用绕过代理会破坏语义且框架限制明显。

## 识别信号

- @Transactional/@Cacheable
- RPC stub
- lazy loading
- 权限检查

## 实现要点

- 代理和真实对象遵守同一契约。
- 明确调用边界与异常语义。
- 框架代理要注意 final/private/self-invocation 等限制。

## 常见误用

- 把业务规则塞进代理。
- 隐藏网络调用成本，让本地接口看起来像廉价调用。
- 代理层层嵌套导致调用链不可观测。

## 常见组合

- Decorator
- Adapter
- Circuit Breaker

## 最小示意

```text
OrderService proxy = TransactionProxy(realService)
```

## 深度分析

### 变化压力
Proxy 通过同一契约控制访问，常用于权限、懒加载、远程调用和事务。它的核心是“访问语义改变但接口保持一致”，不是所有横切代码都应透明隐藏。

### 结构与协作
Proxy 持有真实对象或远程地址，在调用前后处理授权、加载、超时、序列化和错误映射；远程代理必须显式标记成本与取消语义。框架代理要检查 self-invocation、final/private 方法和上下文传播。

### 关键权衡与替代
透明访问降低调用方改造，但会隐藏 I/O、失败和一致性成本。可选功能叠加用 Decorator；不兼容协议用 Adapter；需要统一多组件流程用 Facade。权限代理不应替代领域授权决策。

### 落地与验证
先选择一个边界并写出调用契约，迁移单一路径。测试授权拒绝、懒加载失败、远程超时、重试/取消和事务边界；trace 标明 proxy 类型、目标和网络跳数。若调用方必须知道大量代理细节，改为显式端口。

## 退出条件

当代理不再改变访问语义、只做转发或隐藏成本造成误用时，删除并暴露更明确的接口。
