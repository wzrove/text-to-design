# 外观模式（Facade）

**类别：** GoF / 结构型

## 意图

为复杂子系统提供更简单、面向用例的统一入口。

## 什么时候使用

- 调用一个用例需要协调多个子系统。
- 希望降低外部模块对内部细节的耦合。
- 需要为 SDK 或模块暴露稳定 API。

## 什么时候不要使用

- 子系统本身已经简单。
- Facade 变成承载所有业务的 God Service。
- 调用方确实需要底层高级能力，应保留直接访问通道。

## 识别信号

- 调用方要依次调多个 service
- 对外 API 需要简化
- 模块边界不清晰

## 实现要点

- 按业务用例设计 facade 方法，而不是简单转发每个底层方法。
- Facade 依赖内部组件，外部只依赖 Facade。
- 保持 Facade 薄，复杂领域规则仍应在领域对象/服务中。

## 常见误用

- 把所有系统功能都塞进一个 Facade。
- Facade 只是一比一转发，没有降低复杂度。
- 隐藏重要错误语义。

## 常见组合

- Application Service
- Adapter

## 最小示意

```text
CheckoutFacade.checkout(cmd) -> pricing + inventory + payment + order
```

## 深度分析

### 变化压力
Facade 解决调用方必须了解多个子系统调用顺序、默认值和错误组合的问题。它应按用例提供稳定入口，而不是把子系统的每个方法重新导出。

### 结构与协作
Facade 依赖内部组件并协调调用；事务、权限和领域规则归属于应用/领域层，Facade 只暴露稳定 DTO/错误契约。高级调用方若确实需要底层能力，应提供明确的 escape hatch，不要偷偷绕过边界。

### 关键权衡与替代
Facade 降低耦合和学习成本，但可能成为 God Service、隐藏性能与部分失败。模块内部 API 简单时直接调用；跨服务外部入口用 API Gateway；第三方协议不兼容用 Adapter。

### 落地与验证
先选一个最常用流程画调用时序，抽出一个用例方法并删除调用方重复编排。测试默认值、顺序、部分失败、错误映射和幂等；监控 facade 用例耗时与子系统调用分布。若方法只做一比一转发，说明没有 facade 价值。

## 退出条件

当子系统已经有稳定用例 API，或 facade 继续膨胀成中心服务时，拆分/删除它。
