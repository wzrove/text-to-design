# 适配器模式（Adapter）

**类别：** GoF / 结构型

## 意图

把不兼容接口转换为系统期望的接口，隔离第三方或遗留系统差异。

## 什么时候使用

- 接入第三方 SDK、遗留 API、不同供应商接口。
- 领域层不应感知外部接口细节。
- 要替换供应商但希望上层代码保持不变。

## 什么时候不要使用

- 两个接口本来就兼容。
- 真正需要的是增强或访问控制；应考虑 Decorator/Proxy。
- 适配层包含大量业务编排，说明边界设计可能错误。

## 识别信号

- 第三方 API 侵入业务层
- 多个供应商接口命名/模型不同
- 需要 anti-corruption layer

## 实现要点

- 系统内部先定义稳定端口接口，再为外部系统写适配器。
- 在适配器边界完成 DTO/异常/错误码转换。
- 不要让供应商类型穿透领域层。

## 常见误用

- 适配器只改方法名却不处理语义差异。
- 在适配器里塞复杂业务规则。
- 异常转换不一致，导致上层仍依赖供应商语义。

## 常见组合

- Facade
- Repository
- Dependency Injection

## 最小示意

```text
SmsPort.send(msg) <- AliyunSmsAdapter / TwilioSmsAdapter
```

## 深度分析

### 变化压力
Adapter 处理的是外部接口与内部端口的语义不兼容：命名不同只是最轻的一种，真正风险在错误码、时间、重试、分页和取消语义。先定义内部稳定契约，再评估供应商差异是否值得隔离。

### 结构与协作
业务层依赖内部 Port；Adapter 负责 DTO、认证上下文、错误分类、超时和资源释放的转换，外部 SDK 只出现在基础设施层。更换供应商时替换 Adapter 和装配绑定，不能让供应商类型穿透领域。

### 关键权衡与替代
适配隔离了供应商变化，但会增加映射、合同测试和版本维护。接口本来同构时直接注入；如果要叠加缓存/指标用 Decorator；如果要控制访问或远程替身用 Proxy。复杂业务编排不应藏在 Adapter。

### 落地与验证
先为一个端口建立错误与数据映射表，迁移单一路径并保留旧实现作差分。测试超时、取消、空/异常响应、分页和供应商错误映射；记录 provider、operation、latency 和 retryable 类别，不记录凭证。若 Adapter 需要读取领域状态，重新划分边界。

## 退出条件

当供应商接口与内部契约稳定同构且没有替换/隔离收益时，删除 Adapter，直接依赖实现。
