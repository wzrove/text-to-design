# 享元模式（Flyweight）

**类别：** GoF / 结构型

## 意图

共享大量对象中的重复、不可变内在状态，以降低内存或创建成本。

## 什么时候使用

- 存在海量细粒度对象且重复状态占用显著。
- 可把状态拆成共享的 intrinsic 与外部 extrinsic 部分。
- 性能分析已经证明对象数量/内存是瓶颈。

## 什么时候不要使用

- 没有实际内存压力。
- 共享状态可变，容易引发并发和污染。
- 为了理论优化牺牲代码清晰度。

## 识别信号

- 百万级相似对象
- 大量重复字符串/样式/元数据
- 对象缓存池

## 实现要点

- 共享部分必须不可变或线程安全。
- 外部状态由调用方传入。
- 先 profile，再决定是否引入。

## 常见误用

- 过早优化。
- 把连接池等资源池简单等同于 Flyweight。
- 共享可变对象导致幽灵状态。

## 常见组合

- Factory Method
- Prototype

## 最小示意

```text
glyph = glyphFactory.get(charCode); glyph.draw(position)
```

## 深度分析

### 变化压力
Flyweight 只在大量对象共享不可变内在状态、且 profile 证明内存/创建成本显著时有价值。先区分 intrinsic（可共享）与 extrinsic（每次调用不同）状态。

### 结构与协作
Factory/Pool 按稳定 key 返回共享对象；共享对象必须不可变或线程安全，调用方传入位置、租户等外部状态。缓存有容量、淘汰和生命周期策略，不能把外部资源句柄混进共享状态。

### 关键权衡与替代
共享减少内存但增加缓存命中、并发和失效复杂度。普通对象数量不大时直接创建；连接池是资源复用而非 Flyweight；Prototype 解决复制模板而非共享状态。

### 落地与验证
先提供基线 profile，再实现一个共享热点。测试相同 key 复用、外部状态隔离、并发读、淘汰和缓存满；监控内存、命中率、对象数和 GC。若共享对象出现可变字段，立即拆分 ownership。

## 退出条件

当 profile 不再显示收益、缓存维护成本上升或状态无法保持不可变时，删除 Flyweight。
