# 依赖注入模式（Dependency Injection）

**类别：** 企业应用模式

## 意图

由外部组装器提供依赖，使对象不负责查找或创建其协作者。

## 什么时候使用

- 希望降低具体实现耦合并提高测试替换能力。
- 应用有多个基础设施实现。
- 容器负责生命周期和装配。

## 什么时候不要使用

- 简单纯函数无需注入。
- 注入几十个依赖暴露类职责过重，应该先拆分。
- Service Locator 被误当成 DI。

## 识别信号

- 构造函数注入
- IoC container
- 接口替换测试

## 实现要点

- 优先构造器注入。
- 依赖显式化，避免全局容器查找。
- 在 composition root 集中装配。

## 常见误用

- 字段注入导致依赖隐式。
- 任何对象都从容器 getBean。
- 接口数量过度膨胀。

## 常见组合

- Factory Method
- Adapter
- Singleton

## 最小示意

```text
OrderService(repo, paymentPort, clock)
```

## 深度分析

### 变化压力
依赖注入解决的是对象不应自行查找/创建协作者，尤其在多实现、生命周期和测试替换存在时。它不是给每个函数包一层接口。

### 结构与协作
在 composition root 读取配置并装配具体实现；业务类通过构造器接收最小端口，生命周期（singleton、request、transient）由容器或显式工厂管理。调用方依赖抽象，适配器依赖外部 SDK。

### 关键权衡与替代
显式依赖提升可测试性和替换能力，代价是装配代码、启动失败和容器调试复杂度。纯函数直接传参数；小程序可用手写工厂；Service Locator 会隐藏依赖，不应冒充 DI。多个实现只是常量差异时，配置参数更简单。

### 落地与验证
先把一个外部边界从构造函数注入改起，校验生产装配和测试替身都满足同一契约。测试缺失绑定、生命周期泄漏、循环依赖和关闭顺序；启动日志输出组件图摘要但不输出秘密。若构造器依赖超过 5~7 个，优先拆职责。

## 退出条件

当容器只转发一层且没有替换/生命周期收益时，回退到显式构造或模块工厂。
