# 设计模式决策指南

> 何时读：SKILL.md 的「快速路由」没命中、问题跨了多个层级、或者需要评分和迁移顺序时。
> 停止条件和输出格式见 SKILL.md，不在这里重复。

## 1. 先判断问题属于哪一层

| 问题层级 | 典型问题 | 优先查看 |
|---|---|---|
| 对象创建 | 创建逻辑复杂、需要切换实现、参数很多 | Factory Method / Abstract Factory / Builder / Prototype / DDD Factory |
| 类与对象组合 | 第三方适配、功能包装、访问控制、树结构 | Adapter / Decorator / Proxy / Composite / Facade / Bridge |
| 行为变化 | 算法切换、固定流程、规则链、状态变化 | Strategy / Template Method / Chain / State / Command |
| 应用分层 | 事务、持久化隔离、接口契约 | Service Layer / Repository / Unit of Work / DTO / DI |
| 领域建模 | 身份、值、不变量、聚合、领域规则 | Entity / Value Object / Aggregate / Domain Service / Specification |
| 跨服务可靠性 | 双写、重试、故障隔离、跨服务事务 | Outbox / Idempotency / Retry / Circuit Breaker / Bulkhead / Saga（超时预算并入 Retry） |
| 读写架构 | 写规则复杂、读模型特殊、审计重放 | CQRS / Event Sourcing |

跨层的问题按上表从上往下拆。先修边界（建模、分层），再隔离变化（创建、组合、行为），
可靠性机制最后加。顺序反了，模式就会盖住错误的职责划分。

## 2. 评分与证据门槛

候选模式进实施方案之前先做个轻量评分。评分只干一件事，把设计讨论逼到台面上；
任何一项拿不出证据就记 0 分，不按「以后可能要」加分。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 变化压力 | 没有重复或变化 | 已出现 2 个实现/分支 | 变化频繁且修改容易回归 |
| 边界收益 | 无边界问题 | 能隔离一个局部依赖 | 能保护跨模块/事务/安全不变量 |
| 测试收益 | 更难测 | 可替换一个外部边界 | 可建立稳定的合同/状态测试 |
| 运行时成本 | 需新增网络/持久化/全局状态 | 新增少量间接层 | 需要异步、租约、投影或运维体系 |

总分低于 3，或者「运行时成本」拿到 2 分却没有对应的可靠性、一致性收益，默认保持简单。
分数高也替代不了领域边界判断，先把职责归属搞对，再谈模式。

## 3. 落地顺序

1. 先补基线测试和指标，作为回归依据。
2. 提取稳定端口（接口 + 装配点），扩展点留缝但不预先实现。
3. 按第 1 节的层级顺序落地：先修边界（建模、分层），再隔离变化（创建、组合、行为），最后加可靠性机制。
4. 收尾删掉临时脚手架：一次性转换代码、兼容层、调试字段。留着会变成僵尸抽象。

事件、Outbox、Saga、CQRS 这几类，得先定义事件/命令版本、重复处理和失败恢复再上线，
别让两条事实源并存。

回退由记录的「退出条件」触发，没有单独的扩面流程。执行路径要在落地时就备好：
切换开关能关、兼容层能删。
