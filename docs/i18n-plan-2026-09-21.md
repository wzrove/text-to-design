# i18n 方案（ui / mcp-server / shared 三方）

状态：**B0 / B2 / B3（键化）/ B4（机制）已落地**：面板与 MCP 两侧的文案都已键化，MCP 侧 locale 走
`TEXT_TO_DESIGN_LANG`（默认 `zh-CN`），字段说明在注册期投影。**en 译文已全量补齐**（476 键，未译 0，棘轮钉死在 0 —— 新键必须自带译文）；`shared/core` 运行期文案
（D 类，要改载荷格式，不是换文案载体）与 prompts 正文、4 个工具文件里的拼接描述、诊断通道仍是中文。
结论落 `docs/design-decisions/0016-i18n走语义键加参数，默认语言取系统语言并可手动切换.md`（部分落地）。
**引擎实测未做**：改了 `shared/` 与 `ui/`，需要在设计软件里重载插件才看得到面板效果。
两条已拍板：**插件默认语言直接取 `navigator.language`（归一化后），不进构建期注入、不嗅探宿主**；
**面板内可手动切换（跟随系统 / 中文 / English），选择持久化到 `clientStorage`**。

一句话结论：**不引入 i18n 模式/库；把散落的文案抽成「语义键 + 参数」的纯数据表，locale 只在
入口解析一次、显式往下传，文案只在三个出口渲染。** 这是 `dicts/error-code.ts`「协议层只传
类别、不传展示文案」和 `dicts/unapplied-prop.ts`「该类文案唯一真源」两条既有结论在**语言维度**上的
同一条延伸，不是新架构。插件侧语言 = `clientStorage` 里的用户选择 → `navigator.language` → 兜底；
MCP 侧语言独立走 env。

## 2. 压力（为什么现在动）

1. **已有割裂的先例**：`error-code.ts` 的注释明确写了「分类一旦靠猜，措辞变化就会静默失效」，
   于是把类别固化进协议载荷、格式化收敛到 MCP 边界一处。语言维度是同一件事的另一半：
   今天类别是数据、文案是硬编码，**文案没有任何可枚举的载体**，所以既无法换语言，也无法测「有没有漏」。
2. **同一事实正在手写多份**：`NODE_TYPE_LABEL` 既是面板色点表/类型名的来源，也是 `NODE_TYPE_DESCRIBE`
   （进工具目录）的拼装材料，还是 `core/execute.ts` 报错里 `支持 A|B|C` 的顺序来源。新增类型要保证
   三处一致 —— 这是 0008/0009/0010 反复处理的同一类病，i18n 会把它放大成「三处 × N 语言」。
3. **变化点已出现证据**：仓内已建模两个平台，`figma` 走国际用户路径；`PLATFORM_LABEL.figma` 已是
   唯一保持原样的「英文」词。
4. **成本已经产生**：任何一处文案改动都要在 3 个包里手改，且改完没有回归闸门（现有测试只守
   事实一致性，不守文案完整性）。

**压力尚未成立的判断**：目前只有中文一种真实用户在跑。因此 §5 的 B3/B4（模型侧）与 en catalog
是**可延后**的，推荐先落 B0–B2 的「中文 key 化」（见 §7 降级档）。

## 3. 结论：语义键 + 参数，入口解析，三出口渲染

### 3.1 三层结构

```text
packages/shared/src/dicts/i18n/          # 新增（AGENTS.md：静态字典统一在 shared/src/dicts 下）
├── messages.zh-CN.ts                    # 唯一真源的键 → 模板串（as const）
├── messages.en.ts                       # satisfies Record<MessageKey, string>（键缺即编译错）
├── locale.ts                            # Locale 联合、FALLBACK_LOCALE、normalizeLocale()
│                                        #   （zh / zh_CN / zh-Hans / zh-TW → zh-CN；en / en-US / EN → en；
│                                        #    其余 → undefined）、resolveUiLocale()（优先序，见 §3.2）、
│                                        #   createT()、isLocale()、
│                                        #   LOCALE_CHOICE_STORAGE_KEY（切换器持久化的 key，单点）
└── index.ts                             # 导出 type MessageKey / Locale / 上述纯函数（不导出 t 实例）
```

```ts
// 形态示意（不要求照抄）
export const MESSAGE_KEY_RE = /^[a-z][A-Za-z0-9]*(\.[A-Za-z0-9_]+)+$/;   // 命名规范由测试守
export type Locale = 'zh-CN' | 'en';
export type T = (key: MessageKey, params?: Record<string, string | number>) => string;
export function createT(locale: Locale): T;   // 纯函数、无全局状态（沿 0002：显式注入，不设模块级单例）
```

- **键命名**：`<domain>.<subject>.<aspect>`。例：`nodeType.FRAME`、`error.not_connected`、
  `tool.jsd_create_frame.desc`、`ui.hint.disconnected.title`、`unapplied.layoutMode`。
- **插值**只做 `{name}` 字符串替换：**不引 i18next / formatjs**。理由是本仓三个运行环境差异极大
  （插件 code 侧 `target=es6` 只降语法、不注 polyfill，见 `ui/src/code/plugin.ts:63` 的 `Object.hasOwn` 注释；
  daemon 无 DOM），一份 200 行纯函数就够，引库要付包体 + 沙箱风险（0012 的教训）。缺参时保留 `{param}`
  字面 + 一条 warn，同时在测试里守「同 key 的双语言占位符集合一致」。
- **旧的 label 导出不保留双份事实**：`NODE_TYPE_LABEL` 等改为 `t(\`nodeType.${t}\`)` 后**删除旧导出**
  （删掉后漏改的消费点会编译报错，比留兼容层更安全，同 0008/0009 的口径）。
  枚举类数据（`NODE_TYPES`、`ERROR_CODES`、`LOG_LEVELS`、能力键）**不动**，它们本来就是语言无关的。

### 3.2 locale 只在两个入口解析一次

**插件侧优先序（前者覆盖后者）**

| 级别 | 来源 | 谁定义 |
|---|---|---|
| ① | 用户显式选择：`clientStorage` 里的持久化值 → 本次会话内的切换 | 用户；存储走 `DesignHost.clientStorage`（见 §3.6） |
| ② | **`navigator.language`** → `normalizeLocale()` | UI iframe（**只有它有 `navigator`**） |
| ③ | `FALLBACK_LOCALE` = `'en'` | `shared/dicts/i18n/locale.ts`；不可判定语种时的兜底 |

即：`resolveUiLocale({ stored, navigatorLanguage })`，纯函数、放 `shared` 便于单测（不碰 DOM）。

**为什么不从构建期传入**（用户 2026-09-21 定案）：构建期注入会把「语言」绑到产物上，改语言要重新
构建、重新发版；而语言是**用户**的属性、不是平台的属性。既然 `navigator.language` 现成可用，就让它
当默认值，构建期不参与 —— `__TEXT_TO_DESIGN_DEFAULT_LOCALE__`、`PLATFORM_DEFAULT_LOCALE`、
`ui/vite.config.ts` 的 define **全部取消**。

**兜底为什么是 `en` 而不是 `zh-CN`**：`zh*` 一律归一化到 `zh-CN`（含 `zh-TW`，见 §3.5），所以中文
用户必然命中②，轮不到兜底；兜底真正服务的场景是「`navigator.language` 缺失或给出未识别的语种」
（如 `ja-JP`、`fr-FR`），此时英文比中文更通用。想反过来只改这一行常量。

| 入口 | 解析来源 | 说明 |
|---|---|---|
| 插件（E/F/G 面板与画布提示） | 上表三级 | **解析全在 UI 侧**（`navigator` 只在 UI iframe 里存在），但**持久化必须过 code 侧** —— `clientStorage` 是宿主 API，UI iframe 摸不到。于是多了一对旁路消息：`locale_set`（UI → code）/ `locale_state`（code → UI，启动推一次），落在新增的 `shared/src/locale-channel.ts`。`ui_env` 本身不动 |
| MCP server（A/B/C/D） | ① `TEXT_TO_DESIGN_LANG`（`zh-CN`\|`en`）→ ② 默认 `zh-CN`（§8-1 已推荐保持现状） | 进程级常量，随 `buildServer` 显式注入（沿 0002）。daemon 常驻 → 改 env 需重启 daemon，这与 `probe.warnIfDaemonStale` 的既有机制同源，**不做运行期热切换** |

持久化（已落地）：两侧宿主**都有** `clientStorage`（`@jsdesigndeveloper/plugin-typings/plugin-api.d.ts:45`、
`@figma/plugin-typings/plugin-api.d.ts:407`，签名同为 `getAsync/setAsync/deleteAsync/keysAsync`，全 async），
所以这不是「宿主没能力」，而是「我们没建模 `DesignHost`」。做法见 §3.6。

### 3.3 三个渲染出口，以及明确排除的一条通道

| 出口 | 载体 | locale 源 |
|---|---|---|
| ① MCP 边界 | `tools/list`、`prompts/list`、结果 `content[].text`、`isError` 文本、`followUp` | MCP locale |
| ② 插件界面 | DOM（面板）+ 宿主 toast | 插件 locale |
| ③ daemon 日志 | 落盘文件 + `{type:'log', line}` 推送（`bridge.ts:79` → `ui/bridge/router.ts:78`） | **不 i18n，保持单语** |

③ 排除，并**写进 0016**，否则下次会被当 bug：这条通道传的是**已格式化字符串**，且一半内容由
`daemon/service.ts` 拼 OS 命令（`loginctl enable-linger` / `schtasks /Run`），翻译它既无收益
（日志是诊断物，标明「谁生成的」比「翻得漂亮」重要），又要把 `line` 拆成 `key + params` 改协议。
真要做时的出口条件写在 §7。

**注意一条例外**：UI 侧自己构造、且用户可见的连接提示（如 `bridge/BridgeSocket.ts:49` 的
「服务已确认连接（版本 x）」、`connection.ts` 的状态文案）**属于出口 ②**，就地 `t()`，不要以
「反正是日志」为由塞进 ③。

### 3.4 两处语言不同步是**有意**的

用户可能看到中文面板 + 英文工具描述：因为受众不同（人 vs 模型），两边 locale 源本来就不同。
这不是缺陷，但要写进记录，避免后来者「统一成一个全局 locale」（那会重新把模型侧拖回单一语言）。

### 3.5 面板内切换语言（UI 侧，本次必做）

- **载体**：面板 header 加一个语言选择控件（`跟随系统 / 中文 / English`；默认档 = 跟随系统），放在
  `ml-auto` 的元信息左侧、`LogTrigger` 右侧的工具簇里 —— 那一簇本来就是「面板级工具」的位置，
  不新增区块、不影响 360 宽的排版预算。
- **形态：紧凑下拉，不是原生 `<select>`**（触发器只显示 `中` / `EN` 两个字符）。`<select>` 会按
  **最长选项**撑宽度（「跟随系统 / English」要 70px 上下），而这一行还要放状态徽章、挽救动作与端口。
  也不用 daisyUI 的 `<details class="dropdown">`：原生 `<details>` 不响应 Escape、也不在点外部时
  收起，而这两条在插件面板里都要有。实现用一层 `fixed` 兜底遮罩 + 容器上的 Escape（与 LogDrawer
  同一套），浮层不进文档流，故不影响 `PanelHeightSync` 量出的内容高度（0014）。
- **形态：紧凑下拉，不是原生 `<select>`**（触发器只显示 `中` / `EN` 两个字符）。`<select>` 会按
  **最长选项**撑宽度（「跟随系统 / English」要 70px 上下），而这一行还要放状态徽章、挽救动作与端口。
  也不用 daisyUI 的 `<details class="dropdown">`：原生 `<details>` 不响应 Escape、也不在点外部时
  收起，而这两条在插件面板里都要有。实现用一层 `fixed` 兜底遮罩 + 容器上的 Escape（与 LogDrawer
  同一套），浮层不进文档流，故不影响 `PanelHeightSync` 量出的内容高度（0014）。
- **状态**：新增 `ui/src/i18n/useLocale.tsx`（Solid context）：`{ locale, choice, setChoice, t }`。
  **`t` 必须读 locale 信号**（`const t = (k, p) => translate(locale(), k, p)`）。把它缓存成模块常量
  （`const t = createT(resolved)`）会让切换**静默失效** —— 这是本方案实现期最容易踩的坑。
- **两个跟随动作**：① `document.documentElement.lang = locale()`（`ui.html` 现在是硬编码
  `lang="zh-CN"`，影响屏读器发音与字体回退）；② 面板内所有可见文案（含日志抽屉的档位标签、
  `aria-label`、`title`）都走 `t()`，所以切换是整面板即时生效。
- **「跟随系统」怎么看**：`resolveUiLocale` 顺序为 ① `clientStorage` 的显式选择 → ② 选了「跟随系统」
  时读 `navigator.language` 并归一化 → ③ `FALLBACK_LOCALE`。`choice` 与 `locale` 分开存信号：
  `choice === 'system'` 时 `locale` 随 `navigator.language` 走，否则 `locale = choice`。
- **归一化规则**（`normalizeLocale`，表驱动、纯函数）：`/^zh\b/i` → `zh-CN`（`zh` / `zh-CN` / `zh_CN` /
  `zh-Hans` / `zh-TW` 都进来，繁体也先给简体，因为只有两套文案）；`/^en\b/i` → `en`；其余 → `undefined`
  由兜底接管。
- **持久化**：只在用户**显式**改过选择时才写 `clientStorage`（key 固定为 `LOCALE_CHOICE_STORAGE_KEY`；
  不写「跟随系统」这个初始态 —— 否则用户以后换了系统语言，插件还停在旧语言上）。

### 3.6 为什么默认值只能是 `navigator.language`

两条实证（2026-09-21）：

1. **「嗅探宿主」这条路不存在**：两平台 typings 都没有任何 locale / 语言 / i18n API。
   Figma typings 里 `language` 的三处命中全是 `CodeBlockNode.language` 与高亮语言枚举
   （`plugin-api.d.ts:2960/2982/11482`）；jsDesign typings 只有 `Local styles` 之类的假阳性。
   jsDesign 的 typings 本身就是 Figma API 的 fork（文件头写着 "Figma Plugin API version 1, update 40"），
   两边的 API 面同源。这不是「不推荐嗅探」，是**没有东西可嗅** —— 面板里那句「跟随系统」，
   物理上只能读 webview 的 `navigator.language`。
2. **`navigator.language` 只存在于 UI iframe**：code 侧沙箱的 typings 连 `navigator` 都没有
   （grep 零命中）。这条**反过来决定了架构**：语言解析只能落在 UI 侧，于是不需要任何跨侧消息
   （`ui_env` 保持只有 `canResize`），也不需要 code 侧知道 locale。

**代价（有意接受，别当 bug）**：

- 它读的是 webview / 浏览器 / 系统语言，**区分不了「本包是 figma 包还是 jsDesign 包」**。
  后果：中文系统上装的 Figma 包，默认面板也是中文。用户的出路是面板里的选择器 —— 一次点击，
  且会被 `clientStorage` 记住，所以这是一次性成本，不是每次开面板都要做。
- 取值五花八门（`zh` / `zh-CN` / `zh_CN` / `zh-Hans` / `zh-TW` / `en-US`…），必须配 `normalizeLocale`；
  未识别的语种（`ja-JP`、`fr-FR`）落到 `FALLBACK_LOCALE = 'en'`。
- 若将来确实要「按平台给不同默认」（figma 默认 en、jsDesign 默认 zh），回到 §4.4 的结论：
  只能由 per-platform 的 code bundle 算好、经 `ui_env` 报给 UI，不能写进 UI 常量。

**`DesignHost` 的扩法**（持久化要用）：加一个可选成员，按 0010 一律 async：

```ts
readonly clientStorage?: {
  getAsync(key: string): Promise<unknown>;
  setAsync(key: string, value: unknown): Promise<void>;
};
```

两平台各自一行转发到 `jsDesign.clientStorage` / `figma.clientStorage`。**必须 `typeof` 特性检测 +
`try/catch`**：jsDesign 的 `clientStorage` 是随 typings 一起 fork 来的**声明**，运行时是否实现要实测
（§8-4）；拿不到就静默退化为「会话内有效」，不要因此让面板起不来。

## 4. 硬约束与对策

### 4.1 工具目录体积（0006 + `catalog-budget.test.ts`）

现状：投影后目录 ≤ 500 KB，入参 schema 约 300 KB 是**地板**，2026-09-18 实测超限的后果是
「宿主只索引到 4 个工具，`jsd_find`/`jsd_export`/`jsd_batch` 全检索不到」。
→ **绝不能把两种语言的 description 同时塞进 `tools/list`**。

对策：**注册期按单一 locale 求值**（`bridgeTool` 里 description 已经是注册时拼装，见
`core/registry.ts:270`，天然满足）。加两条门禁（§6-7）：zh 与 en 各自生成的目录都 ≤ 500 KB；
`buildServer` 只接受一个 locale（不存在「双语目录」这条代码路径）。

### 4.2 zod `.describe()` 在**模块加载期**求值

`shared/schemas/*` 的 375 处 `.describe('中文')` 在模块顶层就固化了 —— 模块级无法感知 locale，
直接换成 `t()` 也不成立（此时还没解析 locale）。

对策：schema 保持**语言无关**：`.describe()` 里存 **MessageKey**（`.describe('nodeType.describe')`），
在 MCP 边界加一层 `localizeSchema(zodSchema, t)`，深度遍历 zod 树把 `_def.description` 命中
catalog 的值替换成 `t(key)`，再交给 `registerTool`。要点：

- 只在 `mcp-server` 边界投影。`shared/schemas` 也会被插件侧加载（0012 沙箱化 zod），插件侧拿到
  key 字符串无害（那侧不展示 schema 文案）。
- 遍历要覆盖 `object / array / union / optional / default / lazy / record / effects`（`core/response.ts:44`
  的 `emptyFor` 已经趟过同一棵树，可复用其 typeName 判定方式）。
- **最大风险是「遍历不到 → 字段说明静默消失」**（模型看不到字段含义），所以必须有数量不变式门禁
  （§6-5）：投影后被填上 description 的字段数 ≥ 基线。
- 这是本方案**唯一真正的结构改动**（新增一层边界投影），也是 0016 记录的主体。

### 4.3 静态字典归属

按 AGENTS.md，i18n catalog 放 `packages/shared/src/dicts/i18n/`；`dicts/index.ts` 继续只做纯数据出口，
不导出 `t` 实例（避免出现模块级单例，沿 0002）。

### 4.4 UI 产物两平台共用 → 平台默认语言只能走消息

`ui/scripts/vite-plugin-manifest.ts` 在 `closeBundle` 里把**同一份** `dist/ui.html` 拷进
`dist/figma/` 与 `dist/jsdesign/`。**这条事实本身仍然要记住**（别把平台相关的东西写进 UI 常量），
但在当前定案下它**不构成约束**：语言默认值来自 `navigator.language`，与平台无关，UI 自己就能算，
不需要 code 侧参与。

若将来要改回「平台各给一个默认」（figma 默认 en、jsDesign 默认 zh），唯一可行路径是：由 per-platform
的 **code** bundle 解析后经 `ui_env` 加字段报给 UI（`ui_env` 是 0014 就有的旁路消息，加字段成本很低），
仍然不能写进 UI 常量 —— 同一份 `dist/ui.html` 会被拷进两个平台的包里，写死就等于两平台同语。

## 7. 成本、退出条件、降级档

**成本**

- 两份 catalog 长期同增；键改名要同时改两处 + 全部调用点。
- B4 的 375 处迁移是本方案最大工作量，且迁移期间的失败模式是**静默的**（描述丢了但工具还能调）
  —— 所以先有 #5 门禁再迁。
- 新增一层边界投影（`localizeSchema`），多一处「说明可能不生效」的地方，需要可观测（数量不变式）。
- daemon 换语言要重启；**MCP 侧**语言改 env 要重启（插件侧不重启，见 §3.5）。
- 面板与 MCP 语言可能不同步（§3.4，有意）。
- **默认语言不精确**：`navigator.language` 读的是系统/webview 语言，不是设计软件的语言，也不是
  用户的偏好。表现为「中文系统上装 Figma 包 → 默认中文」。补救靠面板选择（一次性，之后被记住）。
- `clientStorage` 是**可能不存在的增强**（jsDesign 侧只有 typings 声明）：两平台各要一条 `try/catch`
  路径与一次实测，拿不到就退化为会话内 —— 复杂度花在「不因此崩」上，不是花在功能上。

**退出条件 / 回退**

1. Figma 国际化需求撤销 → 去掉 `messages.en.ts` 与 `localizeSchema`（`t()` 从双语言退化为单语言
   直查），**保留 key 层**：消灭硬编码 + 可测这两项收益不依赖第二语言。
2. 需要运行期热切换语言（MCP 侧）→ 升级为响应式 catalog（订阅 locale 变更后重注册工具）。本次明确
   不做，因为要重跑 `registerTool`（目录是对外契约，中途变更会打乱宿主索引）。**面板内切换不属于
   此类**：它只重渲染 UI，不碰目录。
3. `clientStorage` 运行时不可用（实测确认）→ 删掉持久化那一段，选择退化为会话内有效；契约里的
  可选成员可以留着（`typeof` 检测本来就要写），也可以一并删。
4. 若重新要求「figma 默认 en、jsDesign 默认 zh」→ 回到 §4.4：per-platform 的 code bundle 解析后
   经 `ui_env` 加字段报给 UI（`DesignHost` 与消息都已存在，成本一条字段 + 一处分支）。
5. code 侧出现用户可见提示（`notify`/toast）→ 补 `ui_locale` 旁路消息（UI → code，守卫形态同
   `isUiResizeMessage`）。注意两平台 typings 都已带 `notify` + `NotificationOptions`，所以这条路
   随时可能被打开，届时面板选择必须能传下去。
6. 需要复数/性/日期数字格式 → 评估 `Intl.*` 或 `Intl.MessageFormat` 替换插值函数，键格式不变。
7. ③ 日志通道要 i18n → 触发条件是「有非中文用户报障且日志看不懂」；届时把
   `{type:'log',line}` 拆成 `{level, key, params}`，daemon 侧落盘仍存 key（可追溯）。

**降级档（推荐先落）**：只做 **B0 + B1 + B2**（中文 key 化 + 入口 locale 基建），en catalog 留空壳。
工作量最小、不触碰 0006 的体积线、未来要英文只需补一份数据 + B3/B4。**注意：**要 en 覆盖面板就
得先把 `messages.en.ts` 的面板部分补齐（B2 的一半工作量），否则英文用户看到的是中文面板。

## 8. 待决问题（需拍板）

已定（本次拍板，落 0016）：插件默认语言**直接取 `navigator.language`**（归一化后，不进构建期注入、
不嗅探宿主 —— 宿主也没有可嗅的 API，§3.6）；面板内可手动切换（三档：跟随系统 / 中文 / English，
选择持久化到 `clientStorage`）。

仍待决：

1. **MCP 侧默认语言**：保持 `zh-CN`（现状，工具描述已被中文模型用户验证），还是缺省 `en`
   面向国际客户端？→ **推荐保持 `zh-CN`**，等 en catalog 真正可用再切默认。
2. **是否本次就要 en catalog**：面板默认值现在是 `navigator.language`，所以英文系统用户一开面板
   就是英文 —— en 至少要覆盖 B2/面板；建议这次补到「面板 + 工具 title/description」，
   `schemas` 的 375 处 describe 留到 B4。
3. **`.describe()` 的投影约定**：`.describe('nodeType.describe')` 这种「裸 key 字符串」是否可接受
   （代价：schema 文件里看不出人话，可读性下降）；替代方案是给每个 schema 加 `.meta({ i18nKey })`。
   → **推荐裸 key + 数量不变式**，理由是不改 zod 用法、投影层只需看 `description` 一处。
4. **兜底语言 `FALLBACK_LOCALE`**：现定 `'en'`（未识别语种如 `ja-JP`/`fr-FR`、或 `navigator.language`
   缺失时用它）。若要偏中文用户，改成 `'zh-CN'` 只是一行常量。
5. **待实测（B0 内）**：jsDesign 运行时到底有没有 `clientStorage`（typings 是从 Figma fork 来的声明，
   不等于实现）。测法：插件 code 里 `typeof jsDesign.clientStorage?.getAsync` 打一行日志，看面板
   日志抽屉。有 → 按 §3.6 做持久化；没有 → 走退出条件 3。

## 9. 明确不做的事

- **不翻译仓库文档**（README / docs / CHANGELOG 保持中文，它们是给维护者看的）。
- **不引 i18n 框架**（§3.1 理由：插件沙箱 `es6` 无 polyfill、daemon 无 DOM、只有 2 个 locale）。
- **不做运行期热切换 MCP 工具目录**（§7-2）。
- **不从构建期注入默认语言**（用户 2026-09-21 定案）：`__TEXT_TO_DESIGN_DEFAULT_LOCALE__`、
  `PLATFORM_DEFAULT_LOCALE`、`vite.config.ts` 的 define 与 `ui_env.locale` **都不做**。
- **不嗅探宿主语言 API**（§3.6：两平台都没有这个 API；只有 `navigator.language` 这一条可用路径）。
- **不发 `ui_locale` 反向消息**（触发条件 §7-5）；**不做**任何「按 MCP 客户端名字猜语言」。
- **不改写入管线**（0001/0004）与错误分类协议（0013）：i18n 只换文案载体，不动 code 与载荷结构。
