## 压力

三方（`shared` / `mcp-server` / `ui`）的展示文案全部是内联中文硬编码：含中文的非注释代码行实测
shared 644 / mcp 454 / ui 151，zod `.describe()` 约 370 处。具体压力：

1. **文案没有可枚举的载体**，所以既换不了语言，也测不出「漏没漏」。`error-code.ts` 早已把「错误
   类别」从裸字符串收成了协议载荷（正是为了避免「措辞一变就静默失效」），语言是同一件事的另一半。
2. **同一事实已手写多份**：`NODE_TYPE_LABEL` 同时喂面板类型名、`NODE_TYPE_DESCRIBE`（进工具目录）
   与 `core/execute.ts` 的 `支持 A|B|C` 报错。多语言会把它放大成「N 处 × M 语言」。
3. **已有平台差异的证据**：`figma` 走国际用户路径，而面板/工具描述只有中文。
4. **唯一真源缺口的反例已存在**：`PLATFORM_LABEL.figma` 是仓内唯一保持原样的「英文」词 —— 说明
   今天「面板中文名」与「面向模型的描述」被同一份数据绑死，而这两者受众不同、语言需求可以不同。

不做的判断依据：压力不足以支撑 i18n 框架（只 2 个 locale、三个运行环境差异极大），也不足以支撑
运行期热切换（工具目录是对外契约）。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 语义键 + 参数表 + 入口解析 + 出口渲染 | 采用（主） | 唯一同时满足「可枚举、可测、三侧受众不同」的做法；延续 0013/0007 既有口径 |
| 引 i18next / formatjs 等框架 | 排除 | 只 2 个 locale；插件 code 侧 `target=es2017` 只降语法不注 polyfill（同 0012/`Object.hasOwn` 那条教训）、daemon 无 DOM，库要付包体与沙箱风险 |
| 按「猜测 MCP 客户端名字」定语言 | 排除 | 正是 `error-code.ts` 批评过的「靠猜」；MCP 协议没有 locale 字段 |
| **嗅探宿主语言 API** 定默认语言 | 排除（**无此 API**） | 两平台 typings 里没有任何 locale / 语言 / i18n 出口：Figma 的 `language` 三处命中全是 `CodeBlockNode.language` 与高亮语言枚举（`plugin-api.d.ts:2960/2982/11482`），jsDesign typings 只有 `Local styles` 假阳性；且 code 侧沙箱连 `navigator` 都没有。不是「不推荐」，是**没有东西可嗅** —— 这也是默认值只剩 `navigator.language` 一条路的原因 |
| **`navigator.language`** 当默认语言来源 | **采用**（默认值就取它） | 用户 2026-09-21 定案：语言是**用户**的属性，不是平台的属性。构建期注入会把语言绑到产物上（改语言要重新构建发版），而 `navigator.language` 现成可用、无需任何构建改动。代价记在「成本与退出条件」：它读的是系统/webview 语言，中文系统上装 Figma 包默认也是中文 —— 出路是面板选择（一次点击 + 持久化） |
| **构建期注入**默认语言（`__TEXT_TO_DESIGN_DEFAULT_LOCALE__` + `PLATFORM_DEFAULT_LOCALE[platform]` + `vite.config.ts` 的 define） | **撤销**（上一轮曾采用） | 被上一条取代：默认值不再依赖平台，整条构建期注入链（define、平台默认表、code 侧解析、`ui_env.locale` 字段）**全部删除**。留作退路：若将来重新要求「figma 默认 en / jsDesign 默认 zh」，唯一可行路径是 per-platform 的 code bundle 解析后经 `ui_env` 加字段报给 UI（UI 产物两平台共用，见下条） |
| 面板语言选择持久化到 `clientStorage` | 采用（本次纳入） | 两侧宿主**都有**该 API（`@jsdesigndeveloper/plugin-typings/plugin-api.d.ts:45`、`@figma/plugin-typings/plugin-api.d.ts:407`，签名同为 `getAsync/setAsync/deleteAsync/keysAsync`），社区实践中「用户显式选择」本就是高于嗅探的可信来源；代价是扩 `DesignHost`（可选成员 + 两平台转发 + fixtures），且要 `typeof` 特性检测——jsDesign 的声明是随 typings 从 Figma fork 来的，运行时未必实现 |
| UI 常量里写平台默认语言 | 排除（**不可能**） | `vite-plugin-manifest.ts` 把同一份 `dist/ui.html` 拷进 `dist/{figma,jsdesign}/` —— UI 产物两平台共用，写死就等于两平台同语。这也是「平台默认只能走 code → UI」的唯一理由，当前定案下该约束不生效 |
| 面板切换后再发一条 `ui_locale` 给 code 侧 | 本次排除 | code 侧当前没有用户可见文案（只有 `console.*` 诊断），加一条无消费方的协议消息属投机；两平台 typings 都已带 `notify` + `NotificationOptions`，这条路随时可能被打开（见退出条件） |
| daemon 日志一并 i18n | 排除 | 该通道传的是已格式化字符串，且半数是 `daemon/service.ts` 拼的 OS 命令；要翻就得把 `line` 拆成 `key + params` 改协议，而日志是诊断物（见退出条件） |
| 运行期热切换语言 | 排除 | 要重跑 `registerTool`，工具目录中途变更会打乱宿主索引（0006 的后果是工具查不到）。**面板内切换不属此列**：只重渲染 UI，不碰目录 |

## 结论

**不引入 i18n 模式与库：文案抽成「语义键 + 参数」纯数据表，locale 只在入口解析一次并显式传值，
文案只在三个出口渲染。** 插件默认语言取 `navigator.language`（归一化后），面板内可切换且选择持久化。

1. **数据层**：`packages/shared/src/dicts/i18n/`（AGENTS.md：静态字典归 `shared/src/dicts`）。
   `messages.zh-CN.ts` 是键的真源；`messages.en.ts` 用 `satisfies Record<MessageKey, string>` 让漏译
   变成编译错；`locale.ts` 放 `Locale` / `FALLBACK_LOCALE` / `normalizeLocale` / `resolveUiLocale` /
   `LOCALE_CHOICE_STORAGE_KEY` / `createT` / `isLocale`。
   插值只做 `{name}` 替换，不引 ICU。**枚举类数据（`NODE_TYPES`、`ERROR_CODES`、`LOG_LEVELS`、
   能力键）保持语言无关、不动**；label 类导出（`NODE_TYPE_LABEL` 等）迁走后**删除**，漏改的消费点
   靠编译报错暴露（同 0008/0009 口径，不留兼容层制造第二份事实）。
2. **locale 优先序（插件侧）**：① 用户在 `clientStorage` 里的显式选择（读不到则是本次会话内的切换）
   > ② `normalizeLocale(navigator.language)` > ③ `FALLBACK_LOCALE`（`en`，未识别语种/取不到时用）。
   `resolveUiLocale({ stored, navigatorLanguage })` 是纯函数、放 `shared`（不碰 DOM，故可单测）。
   - **不进构建期注入**：`__TEXT_TO_DESIGN_DEFAULT_LOCALE__`、`PLATFORM_DEFAULT_LOCALE`、
     `ui/vite.config.ts` 的 define **全部不做**（用户 2026-09-21 定案，理由见候选表）。
   - 归一化是必需的：`zh` / `zh-CN` / `zh_CN` / `zh-Hans` / `zh-TW` → `zh-CN`（繁体也先给简体，
     只有两套文案）；`en` / `en-US` / `EN` → `en`；其余 → `undefined` 交兜底。
3. **跨侧只多了「语言选择」这一对旁路消息**（`shared/locale-channel.ts`）：`locale_set`（UI → code，
   保存/清除选择）+ `locale_state`（code → UI，启动时推一次存储值）。
   - 为什么不能像上一轮说的那样「全在 UI 侧」：**语言怎么算**确实只有 UI 知道（`navigator` 只存在于
     UI iframe，code 侧沙箱连它都没有），但**选择存在哪**只有 code 能碰 —— `clientStorage` 是宿主
     API，UI iframe 摸不到（也不能赌 iframe 的 `localStorage`，那在沙箱里是实现细节）。两个事实各在
     一侧，所以必须有一条消息把「用户的选择」送过去。这也是实现期唯一超出原方案的发现。
   - 这两条**不进 `PluginRequest`**（不过 daemon、不进 MCP）:语言是面板自己的事，没有外部调用方，
     混进那条契约等于凭空多出工具（同 0014 的理由）。
4. **UI 可切换**：面板 header 一个三档选择器（`跟随系统 / 中文 / English`，默认「跟随系统」）+
   `useLocale()` context；**`t` 必须读 locale 信号**（把它缓存成模块常量则切换不刷新，Solid 下这是
   静默失效）。切换后同步 `document.documentElement.lang`（`ui.html` 现为硬编码 `lang="zh-CN"`）。
   - `choice` 与 `locale` 分开存：`choice === 'system'` 时 `locale` 随 `navigator.language` 走，
     否则 `locale = choice`。
   - 持久化**只在用户显式改过选择时**才写 `clientStorage`（不写「跟随系统」这个初始态，否则用户
     以后换了系统语言，插件还停在旧语言上）。
   - `DesignHost` 扩一个**可选** `clientStorage`（async，沿 0010），两平台各一行转发 —— 但必须
     `typeof` 特性检测 + `try/catch`：jsDesign 的那份声明是随 typings 从 Figma fork 来的，运行时
     未必实现。拿不到就静默退化为会话内有效，**不允许因此让面板起不来**。
5. **MCP 侧独立**：`TEXT_TO_DESIGN_LANG`（`zh-CN`|`en`）→ 默认 `zh-CN`（保持现状）。目录按**单一**
   locale 在注册期求值（`registry.ts:270` 的 description 拼装点天然满足），**绝不允许双语同时进
   `tools/list`**（撞 0006 的 500 KB 线，后果是宿主检索不到工具）。daemon 常驻 → 改 env 需重启。
6. **`schemas/*` 的 `.describe()` 存 MessageKey**，在 MCP 边界新增 `localizeSchema(schema, t)` 深度
   投影成文案后再 `registerTool`。这是本次唯一新增的间接层：`.describe()` 在模块加载期求值，模块顶层
   感知不到 locale，只能把「语言」推迟到注册期。
7. **daemon 日志（落盘 + `{type:'log',line}` 推送）有意不 i18n**，保持单语。UI 侧自己构造的连接
   状态文案不算日志，就地 `t()`。
8. **面板语言与 MCP 语言可以不同步**（人 vs 模型，locale 源本就不同）。这是有意结论，避免后来者
   为了「统一」把模型侧重新拖回单一语言。

## 最小落地

- 角色与职责：`dicts/i18n/` = 键与模板的真源 + 纯函数式的 locale 解析；`useLocale()` = UI 侧唯一的
  locale 状态、`t` 与 `clientStorage` 读写（语言解析**全在 UI 侧**，code 侧不参与）；`localizeSchema`
  = MCP 边界唯一的投影点；`ui/scripts/vite-plugin-manifest.ts` 与 `ui/vite.config.ts` 都**不动**。
- 依赖方向：`shared` 不依赖两侧；`ui`/`mcp-server` 各自创建自己的 `t`（显式传值，无模块级单例，
  同 0002）。
- 落地顺序（每批可独立验收）：B0 地基（表 + `createT`/`normalizeLocale`/`resolveUiLocale` +
  `DesignHost.clientStorage`）→ B1 `shared` 字典 label 迁移 →
  B2 UI 文案 + `useLocale` + 三档选择器 + 持久化 → B3 MCP 工具面/prompt/错误文案 → B4
  `.describe()` 375 处迁移 + `localizeSchema` → B5 守卫收紧 + 本记录回填。**B1 必须早于 B4**
  （`schemas/node-type.ts` 的 describe 依赖 `NODE_TYPE_DESCRIBE`）。
- 推荐先落的降级档：B0+B1+B2（中文 key 化 + locale 基建，`messages.en.ts` 留空壳），不触碰体积线。
- **实现期发现（已回填结论 3）**：`clientStorage` 在 code 侧、`navigator` 在 UI 侧，所以持久化必须
  经一对旁路消息（`locale_set` / `locale_state`）。原方案以为「全在 UI 侧」是把这两个事实混成了一个。
  但默认语言已改为跟随系统，**英文系统用户开箱就是英文**，所以 en 至少要覆盖面板文案，否则英文用户
  看到的是中文面板 —— 这一半工作量省不掉。

## 成本与退出条件

- 成本：两份 catalog 长期同增（键改名要动两处 + 全部调用点）；B4 的 375 处迁移量最大，且失败模式是
  **静默的**（字段说明丢了、工具仍可调），所以先有数量不变式门禁再迁；新增一层边界投影；daemon 换语言
  要重启；**MCP 侧语言面板管不了**（两个入口，有意）；面板与 MCP 语言可能不同步（有意）；
  `clientStorage` 是**可能不存在的增强**（jsDesign 侧只有随 typings 从 Figma fork 来的声明），两平台
  各要一条 `try/catch` 路径与一次运行时实测。
- **多了一对跨侧消息**（`locale_set` / `locale_state`）：两侧各一个分支 + 一个守卫 + 一次启动推送。
  它换来的是「选择跨会话保留」,代价可接受;若哪天判定不值,删这两条消息即可退化为会话内有效
  （退出条件②的另一半）。
- **默认语言不精确**（有意接受的代价）：`navigator.language` 读的是系统/webview 语言，不是设计软件
  的语言，也不是用户偏好。「中文系统 + Figma 包 → 默认中文」就是这么来的。补救靠面板选择（一次性，
  之后被记住）；若这个场景量级变大，走退出条件④。
- 退出条件：① Figma 国际化需求撤销 → 删 `messages.en.ts` 与 `localizeSchema`，**保留 key 层**（消灭
  硬编码 + 可测这两项收益不依赖第二语言）；② 实测 `clientStorage` 在 jsDesign 运行时不可用 → 删持久化
  那一段，选择退化为会话内有效（契约里的可选成员可留可删，`typeof` 检测本来就要写）；③ code 侧出现
  用户可见提示（`notify`/toast，两平台 typings 都已带 `NotificationOptions`）→ 补 `ui_locale` 旁路
  消息（UI → code），把面板选择传下去；④ 若重新要求「按平台给默认语言」→ per-platform 的 code bundle
  解析后经 `ui_env` 加字段（`DesignHost` 与消息都在，成本一条字段 + 一处分支），并在构建期定平台默认值；
  ⑤ 非中文用户报「日志看不懂」→ 把 `{type:'log',line}` 拆成 `{level, key, params}`；
  ⑥ 需要复数/性别/数字日期格式 → 用 `Intl.*` 替换插值函数，键格式不变。

## 验证

- **已落地部分的实测证据（2026-09-21）**：`pnpm run typecheck`（三包 + figma 编译单元）、
  `pnpm run test`（**109 用例**，其中新增 `tests/i18n.test.ts` 17 例 + `ui/src/i18n/useLocale.test.ts` 5 例）、
  `pnpm run lint`（170 文件）、`pnpm run build`（ui 双平台 + mcp）全绿；产物核验：
  `dist/{jsdesign,figma}/code.js` 均含 `locale_set`，`dist/ui.html` 同时含两份 catalog。
  **引擎实测未做**（需在设计软件里重载插件，见下）。
- 不变量测试（`pnpm run test`）：① 键集对齐 zh/en；② 同键占位符集合一致；③ 键名匹配命名正则；
  ④ `packages/*/src/**` 非注释字符串字面量不得含 CJK（白名单显式列出：`dicts/i18n/*`、测试、
  daemon 日志出口、`console.*`）—— 这条是整套方案守得住的关键；⑤ `localizeSchema` 后字段 description
  数量 ≥ 基线（防投影漏分支导致说明静默消失）；⑥ 派生键数 = 枚举长度（`nodeType.*` 等）；⑦ zh 与 en
  各自生成的 `tools/list` 都 ≤ 500 KB；⑧ `resolveUiLocale` 优先序单测（用户选择 / navigator → 归一化 /
  兜底各一例）+ `normalizeLocale` 表驱动（`zh`/`zh-CN`/`zh_CN`/`zh-Hans`/`zh-TW`→`zh-CN`、
  `en`/`en-US`/`EN`→`en`、`ja-JP`/空串/`undefined`→`undefined`）；⑨ 目录投影后仍能被 `fromJsonSchema`
  接受（沿用既有断言）；⑩ `clientStorage` 不可用（`typeof` 无 / 抛错）时 `useLocale` 仍能切换且不抛；
  ⑪ 「跟随系统」档下 `locale()` 确实随输入的 `navigator.language` 变化（防退化成一次性求值 —— 就是
  §结论 4 那个「`t` 缓存成模块常量」坑的自动化版本）；⑫ `clientStorage` 读到脏值时被 `isLocale` 拦下
  并回落，不把面板渲染搞崩。
- 引擎实测（人工，两平台各一次）：**默认语言 = 系统语言**（中文系统看到中文面板、英文系统看到英文面板，
  两平台各看一次，这是本次结论的主断言）；三档各切一次，**整面板即时换语言**（含日志抽屉档位、
  aria-label、tooltip），`<html lang>` 同步；关掉面板重开语言仍在（持久化生效；若 `clientStorage`
  实测不可用，此项改为「回落系统语言」）；`clientStorage` 是否存在（`typeof jsDesign.clientStorage?.getAsync`
  打一行日志看日志抽屉）。

| 2026-09-21 | 执行落地（B0 + B2） | 结论不变,补齐实现期唯一超出方案的发现：**持久化必须走一对旁路消息**（`locale_set` / `locale_state`,新增 `shared/src/locale-channel.ts`）—— `navigator` 在 UI、`clientStorage` 在 code,原方案「全在 UI 侧、不新增跨侧消息」把这两个事实混成了一个。另落两处实现细节：① 中文守卫用**棘轮**（白名单按目录列在测试里,逐批摘除）+ 行内 `i18n-exempt:` 显式豁免,否则「新文案顺手写中文」会把键化侵蚀回去;② 语言名在两侧都写自称（`中文` / `English` 不翻译）。验证：109 用例 + 三包 typecheck + lint + build 全绿;引擎实测待人工 |
