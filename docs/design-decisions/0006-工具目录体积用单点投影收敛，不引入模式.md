# 0006. 工具目录体积用单点投影收敛，不引入模式

- **日期：** 2026-09-18
- **状态：** 已采纳
- **影响范围：** `packages/mcp-server/src/daemon/proxy.ts`、新建 `daemon/compact-schema.ts`、`src/server.ts`（INSTRUCTIONS）、新建 `src/__tests__/catalog-budget.test.ts`
- **相关记录：** 承接 0003 的「不手抄清单」原则；与 0002 的单点装配同向

## 压力

1. **出参 schema 的声明体积远超事实，并已产生可观测回归。** 每个工具的 `outputSchema` 展开是 25.5 KB，同一个工具的真实回包只有 ~0.8 KB（单个文本节点的全字段序列化是 837 B）；53 份声明里只有 11 份内容不同 — `serializedNodeSchema` 被 `results.ts` 的 4 个结果 schema 内联展开，`batch` 的结果再引用它们，同一份 `$defs` 被复制 46 次。
2. **后果不是带宽，是工具不可达。** 下游（宿主）拿 `tools/list` 当工具索引的输入。实测基线：目录 1.13 MB（service 直出）/ 1.64 MB（经 shim 的 stdio 下发），宿主只索引到 53 个工具里的 **4 个**，`jsd_find` / `jsd_export` / `jsd_batch` 按名检索全部落空 —— 调用失败不是执行错误，而是「根本没被看见」。
3. **现有设计已为它让过路。** `proxy.ts` 的节奏常量（`HEALTH_POLL_MS` / `FULL_RESYNC_MS`）当年就是为了回避 1.27 MB 清单的重复拉取而把「快速档/慢速档」撤掉 —— 体积问题被当成带宽问题处理过一轮，没碰到根因。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 单点纯函数投影（JSON Schema → 键名+类型） | **采用** | 只有一个投影策略、没有第二种变体；`syncTools()` 已经是「线格式适配」接缝（已在此改写入参校验报错 `friendlyInputSchema`），出参声明体积属同一职责 |
| Decorator 包装 `BridgeToolDef` | 排除 | 装饰器用于「按需层层叠加职责」。这里是单一固定策略，且被处理的是数据（schema 树）不是行为；包装只增加一跳 |
| Proxy | 排除 | 代理控制访问（权限/事务/懒加载/远程替身），此处不拦任何访问 |
| 在 def 层改 zod（为每个工具换成摘要 schema） | 排除 | 40 处 def 或一张「结果 schema → 摘要 schema」映射表都是**第二份事实** —— 正是 0003 刚修掉的「手抄清单」毛病 |
| 把目录改回按插件连接状态门控 | 排除 | `server.ts` 已记录该做法会让客户端永久卡在 1 个工具（多数客户端不处理 `listChanged`）；目录与服务解耦是刻意修过的行为 |
| Composite + Visitor 遍历 schema 树 | 排除 | 树遍历只有 40 行递归，引入类型层次换来的是间接层而非能力 |

命中「停止条件」：只有一个实现、变化无证据、语言原生能力（递归函数 + 单一出口）足够。

## 结论

**不引入模式。** 一个纯函数（`compactOutputSchema`）+ 复用已有出口（`syncTools`），不加接口、不加类、不加装配。

投影规则（不是裁剪语义）：

- **保留** 顶层键名 + 类型 + `required`，以及数组元素/嵌套对象的键名到 3 层 —— 占位符 `{{id.updated[0].id}}` 的路径必须可见，否则模型写不出编排。
- **丢弃** 嵌套类型细节、`$defs`/`$ref`（先解析再投影）、字段级描述、约束关键字。非根对象键数上限 16，**照声明顺序截断**（`serialized-node.ts` 把身份与坐标声明在前）—— 不写白名单，避免又与接口并行的第二份事实。
- **强制** 每个对象层 `additionalProperties: true`：真实回包字段多于声明，若继承原 `additionalProperties: false`，严格校验的客户端会把合法回包判为非法 —— 比体积更严重。

运行期不变：结果构造与校验走 `core/response` 的 `structured()` / `err()`，用的是 def 上的原 schema，与投影无关。

## 最小落地

- 角色：`compactOutputSchema(schema)` 纯函数，无状态、无 IO；`reportCatalogSize(sizes)` 护栏。
- 接口所在层：`daemon/`（shim 的线格式适配层），不在 `shared/schemas`（那是运行期事实）。
- 装配位置：`syncTools()` 内部，出参经 `compactOutputSchema` 后再 `fromJsonSchema`；diff 指纹与体积读数都从 **JSON Schema 本体** 算（`fromJsonSchema` 的产物带函数，`JSON.stringify` 会少读一个数量级）。
- 一次同步时序：`listTools`（上游）→ 逐工具 `friendlyInputSchema` / `compactOutputSchema` → `registerTool` → 全量读体积 → 越预算 WARN。
- 模型侧补一份「结果键约定」进 `INSTRUCTIONS`（`server.ts`）：出参 schema 已投影，占位符路径的知识不能只活在 schema 里。

## 成本与退出条件

- 成本：新增一个文件 + 一处调用；投影规则变更会改变 diff 指纹，触发已连接会话的重新注册（这是期望行为）。
- 下游目录**地板**是入参 schema（约 300 KB，尚未收敛）。若「上游目录 400 KB 仍会被宿主丢工具」被再次观测到，第三阶段是入参去重（11 个 `jsd_create_*` 的 `$defs`+`$ref` 收敛，22 KB → ~6 KB），而不是继续加深出参投影 —— 投影深度再大就会切掉占位符路径。
- 退出条件：若将来客户端不再把目录当索引输入（例如宿主支持按需拉取 schema），投影可退化为恒等函数，护栏保留。

## 验证

- `packages/mcp-server/src/__tests__/catalog-budget.test.ts`（6 条）：
  1. 单工具出参声明 ≤ 5 KB，投影前后压掉 > 8 倍（实测 892 KB → 96 KB，9.3×）；
  2. 目录合计 ≤ 500 KB（与 `proxy.ts` 的 `CATALOG_WARN_BYTES` 同源）；
  3. 占位符路径仍可见（`updated[0].{id,x,y,z}` / `nodes`+`total` / `exports[].{path,dataUrl}`）；
  4. 不得残留 `additionalProperties: false`；
  5. 每个工具的投影都能被 `fromJsonSchema` 接受（注册路径不炸）；
  6. 空/非对象 schema 保持宽容。
- 端到端实测：stdio 探针 `initialize → tools/list` = 53 个工具 / **467,373 B**（原 1,643,871 B，-72%），0 个 `listChanged`；再经 shim 调 `jsd_find` 返回真实 18 字段节点且 `isError` 未触发 —— 证明放开 `additionalProperties` 后不误伤真实回包。
- 观测：每次全量 sync 打一行 `目录体积: N 个工具 / X KB(出参最大 …)`；越 `CATALOG_WARN_BYTES` / `OUTPUT_SCHEMA_WARN_BYTES` 追加 WARN，不阻断。
