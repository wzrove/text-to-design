# de446d4e. 决策记录改用 8 位短 id 取号，旧数字号只读保留

- **日期：** 2026-10-11
- **状态：** 已采纳
- **影响范围：** `.agents/skills/software-design-patterns/`（`scripts/new_decision.py` 取号与寻址、`SKILL.md` 输出段与参考表、`references/decision-log.md` 创建记录段）、`AGENTS.md` 设计决策段的落盘路径写法、`docs/design-decisions/INDEX.md`（新增行用短 id，既有行不动）
- **相关记录：** N/A（不改 0001–0039 任何一条的正文与文件名；0008 的「台账自管」口径不受影响）

## 压力

1. **取号源是本地文件系统**：`next_number()` 读目录里现有文件名取 `max+1`。多人协作时每人从同一
   基线开分支，两边各自算出的都是同一个号（例如 0040），合并时得到两个同号文件 + INDEX 两行同号，
   而 `--status <号>` 从此有歧义。这不是「概率低」的问题，是**必然**：只要两条分支各建一条记录就撞。
2. **撞了不会响**：脚本只在写自己目录时检查存在性，跨分支的同号在合并前无从发现，合并后也没有
   任何门禁拦着 —— 静默变成两条记录争一个标识。
3. **标识要进上下文**：`SKILL.md` 与 `INDEX.md` 整份进 LLM 上下文，主键长度是要付代价的，
   所以「用 UUID」不等于「把 36 位全写进去」。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 8 位短 id（`uuid4` 前 8 位）+ `O_CREAT\|O_EXCL` 占位 | 采用（主） | 跨分支不共享计数器，随机源天然不撞；独占创建把「同机同一秒各跑一次」也收敛成一个赢家；8 hex 在 4 万条量级下生日碰撞概率仍可忽略，撞了脚本自己换号重试 |
| 完整 36 位 UUID | 排除 | 同样解决撞号，但文件名、正文标题、INDEX 每行、每次「相关记录：xxx」的引用都要多写 28 个字符，而这些文件整份进上下文 |
| 日期 / 日期+时间前缀 | 排除 | 撞点只是从「号」挪到「号+时间」：同一分钟两人各建一条照样撞，且跨分支各自算 `max+1` 的行为一点没变 |
| 保留序号 + 加唯一性门禁（测试或 `O_EXCL` 重试） | 排除（用户定案换主键） | `O_EXCL` 只防同机同时刻，防不住两条分支各自落盘再合并；纯门禁方案等于把解冲突推给人工重编号 |
| PR / 分支号做主键 | 排除 | 全局唯一且可读，但记录常常在开 PR 之前就要落盘，那一刻取不到号 |
| 把 0001–0039 一起换成短 id | 排除 | 38 个文件重命名 + 全仓 720 处数字串引用（混着年份、端口等假命中，要逐条判）+ 历史 PR 与外部文档里的旧编号全部失效；收益只是「一套主键更好看」 |

## 结论

**新记录用 8 位十六进制短 id 做主键，旧数字号只读保留。** 取号从「读目录算 max+1」改成「随机短 id +
独占创建」，撞号在同一台机器上由 `O_EXCL` 兜住、跨分支由随机源兜住。`--status` / `--supersedes`
两种形态都认（`0007`、`0007-标题.md`、`a1b2c3d4` 都行），旧记录的文件名、正文标题、相互引用一字不改。

## 实施方案

- **目标形状（全量）**：`new_decision.py` 内 `claim_record()` 负责取号 + 独占创建（撞了重试，最多 20 次），
  `normalize_ident()` / `ident_of()` 是唯一的双形态解析点，`find_record()` / `set_record_status()` /
  `set_index_status()` / `update_index()` 一律按标识工作，不再持有 int 序号。INDEX 里数字行仍按号插入
  原位，短 id 行没有可比顺序一律追加表尾（仍在「依赖关系」之前）。文档侧：`SKILL.md` 输出段与参考表、
  `references/decision-log.md` 创建记录段、`AGENTS.md` 落盘路径写法同步改成短 id。
- **本次不做**：不迁移 0001–0039；不给短 id 加语义（不做 `figma-xxxx` 前缀）；不加「标识唯一性」门禁测试
  （主键本身已经不依赖分配顺序）；不改 `INDEX-2026.md` 归档格式。

## 成本与退出条件

- 成本：仓库里两套主键并存，读到 `相关记录：0013` 与 `相关记录：de446d4e` 需要知道前者是旧号；
  短 id 不可口算，定位记录要靠 INDEX 搜标题而不是凭记忆报号；脚本多约 30 行解析与占位逻辑。
- 退出条件：若将来要求「标识必须人可读」（例如缺陷台账要人手抄号对账），出路是给短 id 建一张
  `号 → 短 id` 的别名表放在 INDEX 顶部，而不是回到 `max+1` 取号。

## 验证

- 不变量测试：无新增（主键不再依赖计数器，撞号不再产生静默重复）。
- 顺带修掉一个既有缺陷：`ROW_RE` 只认裸号行 `| 0039 |`，而本仓 INDEX 的行首是带链接的 `| [0039](0039-xxx.md) |`，于是「插到表尾」一直退化成插到文件末尾（0039 那条就被甩到了 「更早的记录」之后）。现在两种形态都认，短 id 行确实落在表内、`## 依赖关系` 之前。
- 手工用例（scratch 目录跑通）：新建两条 → 均为短 id 且追加表尾；`--status 0007` 能改旧数字记录；
  `--supersedes 0007` 把旧记录标成「已被取代」并同步 INDEX；旧目录无 0007 时只告警不静默跳过。
- 指标与日志：`INDEX.md` 体积增长 = 每行多 4 个字符（`0040` → `de446d4e`），受既有文档预算守。
