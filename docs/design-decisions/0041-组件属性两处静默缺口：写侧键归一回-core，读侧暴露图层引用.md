# 0041. 组件属性两处静默缺口：写侧键归一回 core，读侧暴露图层引用

- **日期：** 2026-10-10
- **状态：** 已采纳（Figma 真机已复验，2026-10-15）
- **影响范围：** `shared/`（`core/{component,serialize,host}.ts`、`schemas/{platform,serialized-node,split-ops}.ts`、新增 `__tests__/component-property-keys.test.ts`）、`ui/`（`code/jsdesign/sync-guarantee.ts` 缺口登记）、`mcp-server/`（`tools/{prompts,components}.ts`）、`.changeset/component-property-gaps.md`
- **相关记录：** 0007（不允许静默失效）、0023（组件属性读写形态：一份形态知识只写一处）、0025（槽位由类型推导，不暴露两套词汇）、0017/0019（MG 键归一留在门面）、0032（平台差异只落声明表与投影点）、0024（`boundVariables` 原样透传）

## 压力

两处缺口都在「组件属性」这条读写链上，由 2026-10-10 用 Figma 真机搭「微信 · 通讯录」页的同一批操作暴露（复用「会话行」组件铺 3 行联系人）。

**① 写侧：键形态从没归属，文档却承诺已归一。**

`setInstanceProperties`（`core/component.ts:210`）把 `properties` 的键**原样透传**给 `inst.setProperties()`，中间零归一。而 Figma 对**组件属性**（BOOLEAN / TEXT / INSTANCE_SWAP）只认带唯一后缀的完整键 —— 真机四连测，短名一律失败：

```
摘要    → in setProperties: Could not find a component property with name: '摘要'
显示铃铛 → ...'显示铃铛'
头像    → ...'头像'
标题    → ...'标题'
```

（`Size: 'Large'` 那种免后缀的写法只对**变体属性**成立，见 Figma `plugin-api.d.ts:9552` 的示例语境；本文这个组件不在 COMPONENT_SET 里，12 个属性全是组件属性。）

三处文档却都写着「门面会自动归一，传名字即可」：`schemas/split-ops.ts:197`（入参 schema 的 describe）、`mcp-server/src/tools/prompts.ts:610`（`component-property` 配方 §4）、`mcp-server/src/tools/components.ts:149`（工具描述本体）。实现里只有 **MG 一处**做了归一（`mastergo/node-facade.ts:627` 的 `remapPropertyIds`），而那里的注释自承只兜得住 BOOLEAN/TEXT —— **INSTANCE_SWAP 这类走不通**。Figma 侧一处归一都没有（host 是原生对象），jsDesign 侧只收字符串、本来就是按名字。

0023 已经把 `setProperties` 的**值**形态收成「一份知识只写一处」，并由第四类表（`dicts/platform-value-domain.ts`）登记；**键**形态从没进过任何表 —— 这就是漏掉的那一格。代价：调用方按文档传短名，得到的是一句没有上下文的引擎报错，且**必须在真机上撞一次才知道文档是错的**。

**② 读侧：看不见「哪个属性驱动哪个图层」，于是同一件事能做错而不自知。**

`会话行` 的 12 个属性是**成对**存在的（`摘要`/`摘要2`、`时间`/`时间2`、`显示铃铛`/`显示铃铛2`、`显示未读`/`显示未读2`、`显示分隔线`/`显示分隔线2`），只有一组连着可见图层。真机表现：

- 只写不带后缀那组 → `componentProperties` **全部回读为新值**、`setProperties` 回包 `ok=true`，画布上摘要/时间/铃铛**纹丝不动**；
- 两组都写 → 画面才变。

这是 0007 要根除的形态本身：回包成功、结果不对，且**没有任何信号提示哪一组是活的**。判据其实在文件里明摆着（原实例「钟启辉」的 `摘要`=「[118 条] X I: [图片]」而 `摘要2`=「答辩答完了呀」，页面显示后者），但那要靠人去比对别处的数据。

引擎有一手事实：Figma `plugin-api.d.ts:6545`、MG `dist/index.d.ts:2406` 的 `componentPropertyReferences`（`{visible|isVisible, characters, mainComponent} → 属性键`）。仓库**已经**在写侧用它（`figma/ops.ts:471` 绑定、`mastergo/ops.ts:568` 绑定与回读校验），但**没进读路径** —— 所以调用方只能靠试。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 写侧键归一收进 core（不引模式，一段纯函数） | 采用 | — |
| 只在 Figma adapter 里包一层归一 | 排除 | 对齐 MG 门面的形制看似对称，但键形态这处差异仍然没有归属，且三平台各写一套；0023 的取向是「一份形态知识只写一处」 |
| 只改文档：键必须与读到的键逐字一致 | 排除 | 承诺已经写出去（三处），收回等于把成本转给调用方；且引擎那句报错没有上下文，失败体验不改善 |
| 读侧原样透传 `componentPropertyReferences`（对齐 0024 的 `boundVariables`） | 排除 | 会把 0025 刚决定藏起来的 Figma `visible` / MG `isVisible` 差异**重新暴露到读路径** —— 0025 的立论正是「不能有两套词汇」 |
| 读侧归一到一个槽位词汇后暴露 | 采用 | — |
| 新增 warnings 通道做「写后孤儿校验」 | 排除 | 有了 references，「哪个属性没连到任何图层」就是集合差，读侧自然看得出；先不为此加通道（0007 的留痕已由读侧事实承担） |
| 保持简单：两处都只改文档 | 排除 | 两处都是「回包成功、结果不对」，正是 0007 要根除的形态 |

## 结论

**不引入模式。** 两处都是**既有契约成员与既有引擎事实的补齐**，不是新机制：

1. **写侧**：键归一收进 core 的 `setInstanceProperties` —— 写之前按实例自己的 `componentProperties`（已是契约成员，`core/host.ts:159`）把键补成完整键。
2. **读侧**：把引擎已有的 `componentPropertyReferences` 加进序列化，槽位键**归一到一套词汇**（沿 0025）。

归一都遵循同一条纪律：**能唯一确定才动手，不确定就点名，绝不猜**。

## 实施方案

- **目标形状（全量）**
  - **写侧**（`core/component.ts`，纯函数 `normalizeComponentPropertyKeys`）：
    1. 键精确命中实例的 `componentProperties` → 保留；
    2. 否则取「最后一个 `#` 之前」的基名匹配 → **唯一命中**才改写成完整键；
    3. 命中 **0 个** → 原样透传（变体属性不在 `componentProperties` 里，不能误伤；MG 实例侧属性表实测常为空，同样落这里）；
    4. 命中 **≥2 个** → 抛错并**列出候选完整键**（歧义不猜）。
  - **读侧**：`NodeSkeleton` 加可选成员 `componentPropertyReferences?: { visible?; characters?; mainComponent? }`；`core/serialize.ts` 守卫式读（同 `variantProperties` 的摘要字段纪律：getter 抛就只丢它）；`schemas/serialized-node.ts` 的 TS 接口 + zod 各加一处可选；槽位键归一到 `visible` / `characters` / `mainComponent`（MG 的 `isVisible` 映射过来）。
  - **扩展点**：MG 的 propertyId 归一仍留在门面（0017/0019 的归属不动）；将来若某平台的键不符合「基名 + `#` + 标识」规律，把归一按平台降级为「不归一 + 文档要求逐字传」—— 落点只有 `normalizeComponentPropertyKeys` 一处。
- **本批做**：上述两处；四处文档纠错（`schemas/split-ops.ts` 的 describe、`mcp-server/tools/components.ts` 的工具描述、`component-property` 配方 §4 与 §6）；9 例单测。
- **登记落点（刻意不进域表）**：新字段的「哪几个平台有」由 **schema 注释 + 契约注释 + `jsdesign/sync-guarantee.ts` 的缺席断言**三处共担，**不**写进 `dicts/platform-knowledge.ts` —— 那张表装的是「变量 / 组件 / 变体」三个**能力面**的事实；而 `componentPropertyReferences` 是一个**只读出参字段**（不像 `componentProperties` 那样既是写入口又是读字段），它的归属是线格式（schema）与缺口断言（sync-guarantee），塞进域表等于给「一个事实」开第二份。
- **本批不做**：写后孤儿校验（warnings 通道）；jsDesign 侧的引用读取（`plugin-api.d.ts` 全文零命中该声明，属**接不了**，与「未接」分开写）；把槽位词汇升格为入参（0025 已排除）。

## 成本与退出条件

- **成本**：写侧每个实例多一次 `componentProperties` 同步读（序列化时本来就读它，同量级）；读侧多一个可选字段（仅组件内子层有值，普通节点不出现，序列化体积不变）；三处文档要跟着改。
- **退出条件**：若真机发现某平台的键形态不满足「基名 + `#` + 标识」（例如后缀里还带 `#`），归一即失效 —— 届时按平台降级为「不归一」，并把该平台的键形态写进第四类表旁边（与值形态同处），而不是继续在归一里打补丁。

## 验证

- **不变量测试**（`packages/shared/src/__tests__/write-path.test.ts` 同目录）：精确键不被改写；基名唯一命中改写成完整键；多头命中抛错且错误里含全部候选；未知键原样透传（不误伤变体属性）；属性表为空时不介入。
- **边界**：INSTANCE_SWAP 短名在 core 归一后仍要被 MG 门面接住；`componentPropertyReferences` 在无引用节点上应缺席（不是空对象）。
- **真机（Figma，2026-10-15 已跑）**：建 `TDD41-会话行` 组件（TEXT 子层 `摘要`）→ `figma_component_property_add{name:"摘要", type:"TEXT", sublayerId:<子层>}` 回 `{propertyName:"摘要#177:0", boundSublayerId:"177:1348"}`，此后：
  ① **读侧**：`jsd_find` 组件子层回 `componentPropertyReferences:{characters:"摘要#177:0"}` ⇒ 属性↔图层一次选对（正是本条要暴露的那一格）；
  ② **写侧短名**：`jsd_set_instance_properties{properties:{摘要:"短名写入-OK"}}` → 实例子层 `characters` 变「短名写入-OK」⇒ core 归一把基名补成完整键，引擎收下；
  ③ **写侧完整键**：`{"摘要#177:0":"完整键写入-OK"}` 同样生效 ⇒ 精确键不被改写。
  两条写路径都落在回包 `updated` 里（无 warnings / skipped）。测试节点已删净：`jsd_find name:"TDD"` 回 0 条，`jsd_get_page` 的 `count` 回到 0。
