# 0020 平台差异不重定义工具：三档机制继续承载，建组件改由 core 统一带子节点

## 压力

接第三平台 MasterGo（0017）后，真机联调暴露三个「平台差距」：

1. `jsd_create_component` 只出 100×100 空壳，建一个带内容的组件要走
   「建壳 → resize → 建内容帧 → reparent → 内层归零」5 次调用（`core/component.ts:24` 明确写了「只建空壳」）。
2. `children` 里传 `type: "COMPONENT"` 被静默降级成 FRAME（`dicts/node-type.ts:57` 的
   `CREATABLE_NODE_TYPES` 不含 COMPONENT，注释写明「走组件通道，不在此列」）。
3. 变体集内 16 个变体在 MG 上重叠于同一坐标，集合尺寸只显示单个变体（`host.ts:117`
   combine 后只 `appendTo`，没设布局也没 resize）。

同一时段出现「要不要按平台各定义一套工具」的提议。压力是真实的（三平台、已产生联调成本），
但根因不是工具抽象不足：MG 官方类型 `@mastergo/plugin-typings/dist/index.d.ts` 里
`mg.createComponent(children?: SceneNode[])`（1407）、`ComponentSetNode` 的
`flexMode / flexWrap / itemSpacing`（2590-2601 经 `FrameContainerMixin`）与 `resizeToFit()`（3083）
全都有 —— 是本仓 adapter 漏接原生能力。

## 结论

**不引入按平台的工具族（不搞 Strategy/Abstract Factory 那套「三平台各一套工具」）。**

平台差异继续收敛到既有三档机制，本次修复落在 **core 层**（平台无关的通用管线），不动工具面：

- 属性级：`dicts/capability.ts` 的能力门控（0004 / 0007）
- 工具级：每个工具的 `platforms` 名单 + `platformNote`（`tools/create.ts:172`、`tools/nodes.ts:126`、`tools/platform.ts:22`）
- op 级：`jsd_platform_op` 通用通道 + ping 下发 `platformOps` 名单（0019）

新增能力时先问「能不能用可选字段 / 能力门控 / platformOps 表达」，能就不加平台分支。

记录：新建（本文件）。

## 理由与排除

- 命中信号（可观察，非最佳实践）：
  - 全仓平台 `if` 分支只有 9 处，且都不在工具层 —— `ui/scripts/vite-plugin-manifest.ts`（2）、
    `ui/vite.config.ts`（1）、`mcp-server/src/daemon/service.ts`（6）。工具层 0 处平台分支，
    差异是**声明式**表达的（`platforms` 名单），不是 `switch`。
  - 三平台 adapter 已经各自一份 `host.ts`（0017 的「门面投影」），加第四平台的成本 = 加一个 adapter，
    不是改工具面。
  - 本次三坑共性根因是 adapter 漏接，证据是 MG 类型里原生能力齐备。
- 排除 Strategy（按平台选工具实现）：工具面已有等价的、更便宜的表达（`platforms` 名单 + 门控 + op 通道），
  再加一层策略对象只是把同一事实抄第二份，违反 0008/0009「同一事实不手写多份」。
- 排除 Abstract Factory（成套切换产品族）：产品族（adapter）已经存在且工作正常，缺的是族内成员的能力补齐，
  不是族的装配方式。
- 排除「按平台各出一套工具」：工具目录体积有硬门禁（0006 / `catalog-budget.test.ts`），
  三平台各一套 = 目录 ×3 直接撞线；且平台语义从「工具内部处理」变成「调用方记住三套工具」，
  把成本转嫁给调用方，与 0017「平台专属约定不进通用层」反向。

## 最小落地

1. `shared/schemas/execute-schemas.ts`：导出 `childNodeSchema`（现为模块私有，第 44 行）。
2. `shared/schemas/split-ops.ts`：`createComponentSchema` 增 `children`（同上数组，
   max 100）与可选 `width` / `height`；`ids` 改为可选（建组件本不需要源节点）。
3. `shared/core/component.ts`：`createComponentNodes(host, ctx, params)` —— 建壳后逐个
   `buildNode(host, ctx, child, component)` 落子节点，最后按 `width/height` 压尺寸。
   **走通用 buildNode 管线，不走 `mg.createComponent(children)` 那条平台专属分支**
   —— 后者会把「带内容建组件」变成 MG 独有能力，Figma/jsDesign 的 `createComponent()` 无 children 参数，
   立刻产生新的平台分叉。
4. `ui/src/code/plugin.ts`：`create_component` 分支传 `ctx` 与 `children`。
5. i18n：`createComponent.description` / `description2` 去掉「只能建空壳」的表述（zh-CN + en）。

时序（一次 `component_op` 请求）：建壳 → 命名 → 逐个 buildNode（含子树的写入/布局/回读回收，
与 create 路径同管线）→ 压尺寸 → 滚动定位 → 序列化返回。三平台同序。

## 成本与退出条件

- 成本：`createComponentNodes` 多一个 `ctx` 参数（与既有 `combineAsVariantsNodes(host, ctx, …)` 同形）；
  无新增状态、无新增异步跳数、无新增持久化。工具数量与目录体积不变。
- 退出条件（满足任一即回到本记录重新评估）：
  - 同一语义在两平台的**参数形状**不同，且无法用可选字段表达（只能整工具分叉）；
  - 单个平台的 `platformOps` 超过 ~10 个（现 MG 5 个），通用通道描述体积失控；
  - 出现「同一工具在 A/B 平台语义不同」（现在的差异都是「有/没有」，不是「语义不同」）。

## 验证

- `pnpm run typecheck`（`tsc --noEmit`）+ `pnpm run test`（含技能文档体积门禁、catalog 预算、i18n）。
- 不变式：`createComponentSchema` 仍可被「只传 ids + name」的旧调用满足（向后兼容）。
- 真机（MG，插件重载后）：一次 `jsd_create_component` 带 `children:[{type:"TEXT",…}]` 应直接产出
  带文本的 COMPONENT，无需 reparent；作为组件合并进变体集后 `variantProperties` 仍可解析。
- 回归：Figma / jsDesign 各跑一次同一调用，确认行为一致（这是本次选择 core 层修复的直接验收点）。
- 未启用 `mg.createComponent(children)`：若日后真机证明 buildNode 管线在组件壳上有偏差，
  再开新记录评估，不在本次顺手加平台分支。
