# 3f364c28. MCP目录精简档提议：核心工具常驻与低频能力按需发现

- **日期：** 2026-11-01
- **状态：** 已采纳
- **影响范围：** mcp-server 工具注册、执行体与目录投影
- **相关记录：** 0003、0006、0030、0032、9c4b0406、4d4e2570；补充目录优化方案，不取代前次审查的缺陷结论。

## 压力

用户指出只去掉两个聚合入口无法明显优化工具数量。当前源码工具目录经现有出参投影后仍有 58 项、443,575 UTF-8 字节；十个 per-type 创建工具占 213,102 字节，其中输入 schema 占 186,284 字节。

仅移除两个 manage 入口约省 15,833 字节。更大的压力是所有低频能力完整 schema 都常驻目录，以及内置能力登记与公开 MCP 工具登记绑在一起。

## 候选与排除

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 核心工具常驻、低频 schema 按需查询、复用 batch 执行 | 建议试点 | 明显缩小工具目录，同时沿用原有专责能力、参数校验与告警 |
| 合并成一个超大 create/update/manage 工具 | 排除 | 回到大量可选字段、op 分流与风险含混；减少名字不保证减少 schema 或调用错误 |
| 随每次查询动态注册工具 | 暂不采用 | 会引入目录变更、客户端缓存、共享 daemon 会话之间的状态与撤销问题 |
| 只删两个聚合入口 | 不足 | 去重有价值，但工具数与字节数收益都有限 |
| 引入工具搜索服务或嵌入检索依赖 | 不采用 | 现有固定能力表按组与名称检索即可先验证，不需要新服务 |

## 结论

先用简单函数分开“登记能力”和“暴露工具”。提供两个启动期稳定档位：兼容档保持现有 58 个公开工具；精简档试点 25 个现有核心工具加一个 jsd_describe_tools，共 26 个公开工具。不在会话内随插件连接状态或模型搜索动态改变目录。

精简档已按下述方案实现；数量与体积改善尚不能证明真实模型任务更准确，默认仍为兼容档。

## 实施方案

1. 将现有工具定义、schema、executor、annotations、hook 登记为一次能力源；公开注册是独立投影。避免把未暴露能力从 executor 删除，也避免为 describe_tools 另写一份 schema。
2. 精简档仅暴露核心工具。低频几何、布尔与轮廓、变体构建、实例解链、导入、覆盖快照、样式管理、平台操作等仍保留内部执行能力。
3. jsd_describe_tools 按类别、名称或简短查询返回候选；只对选中的少量能力返回完整输入 schema、结果键与风险说明。分页/限量，不能一次把其余全部 schema 再塞回上下文。
4. 低频能力通过单步或多步 jsd_batch 执行，继续走原 executor 的参数验证、平台门控、取消、超时及漂移检查，不允许调用者绕过工具协议直连 bridge。独立注册的 prompt fallback 若也要在此路径可用，需先纳入相同的可执行能力登记，而非仅复制名称。
5. 说明精简档的调用规则：公开工具直接调用；其余先发现 schema，再用 batch。skills 与错误提示须遵守此规则，不能继续把隐藏名称当作可直接 tools/call 的工具。
6. 档位按 daemon 启动配置决定。共享该 daemon 的所有会话使用同一档位；若确需并存两档，使用隔离实例，不在请求期间改共享目录。切换后重启并重新协商客户端目录。
7. 兼容档保持旧直接调用；精简档不承诺隐藏工具仍能直接 tools/call。批次可调用内部能力与协议工具可直接调用是两件事。

### 配套体积优化

- 先统一最终目录的 UTF-8 预算，而非字符串 length；将工具数、输入、输出、描述各部分分开统计。
- 第二优先级是十个创建工具的重复字段描述与不适用字段。保留真实类型、必填项和关键约束，不能简单截断或放宽输入校验换体积。
- mcp.instructions 保留路由与必要约束，长流程留 skills；工具描述只保留该工具的用途与局部陷阱，字段限制留在对应 schema。写入后按实际命中返回 warnings，避免全目录反复附加同一长说明。
- 输出投影目前只在 stdio proxy 执行；如支持其他直接连接方式，应在共同公开投影点考虑同一瘦身规则，保持内部完整结果验证。不要让仅 HTTP 客户端继续拿到全量重复输出 schema。
- 别把维护源文件不重复误当作线上传输不重复；同一常量被拼进多个描述，线上仍按多份占空间。

## 测量与验收

通过真实 SDK 内存连接读取当前源码 tools/list，再按现有 compactOutputSchema 投影，计算 JSON 的 Buffer.byteLength，结果：

| 目录 | 项数 | UTF-8 字节 | 输入 schema 字节 | 输出 schema 字节 | 描述字节 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前全部工具 | 58 | 443,575 | 250,426 | 101,888 | 39,668 |
| 25 个现有核心工具候选 | 25 | 183,153 | 102,779 | 36,813 | 23,667 |
| 10 个 per-type 创建工具 | 10 | 213,102 | 186,284 | 14,100 | 5,097 |

核心候选目录比全部工具约少 58.7%；未包含新增 describe_tools 自身 schema 与查询返回成本，不能将该数字宣称为最终上下文或调用耗时降低幅度。没有运行测试套件、build、改变在线目录或写设计画布。

后续应在相同模型与任务下比较精简档与兼容档：首次读取目录与按需 schema 的总字节/模型 token、发现调用数、画布往返数、工具误选率、参数失败率和完整任务耗时。任务至少覆盖整屏设计、批量改文案、图表、变体构建、样式管理、结构修复。

## 成本与退出条件

- 成本：低频操作多一次发现往返；兼容档与精简档都需验证；工具描述与 skills 要同步入口规则。
- 只有依靠发现减少的常驻上下文大于新增查询开销、且真实任务成功率不下降，才考虑把精简档设为默认。没有测量前保留现有默认行为。
- 若某项能力在常用任务里反复触发发现，把它提升到核心组；核心列表按行为证据调整。
- 若发现过程持续误选或增加整体耗时，恢复兼容档，仍可保留已验证的描述和 schema 瘦身。
- 现有启动路径、池租约、导出覆盖问题先修复，保证对比测量基于可靠运行；本提议不替代这些修复。

## 实施与验证（2026-11-01）

- 新增 shared/dicts/mcp-tools.ts：核心工具、兼容旧入口、分类与双语引导；注册能力元数据和 executor 存入每个 McpServer 的 WeakMap 目录。
- TEXT_TO_DESIGN_TOOL_PROFILE=full 为默认兼容档，公开原有 58 个工具；compact 为 26 个。原生 prompts/resources/skills 保持可用，档位只在装配时确定。
- jsd_describe_tools 可分页查摘要、每次按最多 3 个名字取完整输入 schema；隐藏能力通过原有 batch 执行。两个 prompt fallback 也进入同一能力目录；compact 不登记两个旧 manage 入口。
- 输出 schema 投影移到 core 的公共发布边界，内部结果仍走完整 schema；proxy 保持兼容投影。预算改为 UTF-8 字节。instructions 和 batch 描述缩短，完整流程留在 skill 引用中。
- 附带修复：统一源码与发布 skill 路径，构建复制前验证配方元数据与非空正文；prompts 全集从扫描结果派生；实例池改独占租约、满池返回 503，SDK 独立持有的订阅流不持续占用已断开实例；多 ids + 单文件 savePath 在写盘前拒绝；平台聚合操作按最强副作用声明；漂移 hook 显式绑定固定 op，并按服务实例查询 executor。
- 新增或更新回归用例覆盖档位隔离、能力发现、隐藏能力的 batch 调用、目标父层复核、导出保护及租约交错释放。按用户要求未运行测试套件。
- 本地 tsc --noEmit 覆盖 mcp-server/shared/ui/Figma/MasterGo/website/telemetry 与根项目，全部通过；未运行 lint、build，未重启 daemon 或修改设计画布。
- 真实 SDK 内存连接验证 daemon→proxy→客户端：full 为 58 项、434,964 字节；compact 为 26 项、177,994 字节；直连与 proxy 数值一致。两档均有 11 个 prompts、1 个 skill；最大单工具输出 schema 为 3,629 字节。compact 的隐藏 jsd_get_prompt 经 batch 读取成功。相对提议时原目录 443,575 字节，精简目录减少约 59.9%。
- 尚待用户：build 后重载对应平台插件、以指定档位重启 daemon 并重连客户端；运行测试与真实设计任务，核实发布产物启动、HTTP 并发和整体模型成本。未把离线目录检查等同于发布或真机验收。
