## 压力

skills 附录同时作为 prompts/resources 的源文件，内容编辑已影响启动。工具目录没有同名重复，但存在聚合入口与专责入口重叠；注册、执行体登记与发布目录路径也未完全统一。

本轮评审覆盖工具/提示词/资源/skills 注册、构建资源定位、代理目录投影、daemon 实例分配，以及关联的导出行为。没有运行测试、build、重启 daemon 或修改设计画布；不代表全部插件引擎行为、遥测与平台操作均已验收。

## 发现（按优先级）

### P1：发布后配方路径错误，进程在注册前退出

位置：`packages/mcp-server/src/skills/entries.ts:33`、`src/tools/recipe-catalog.ts:153`、`scripts/gen-skills.ts:27`。

entries 以自身 import.meta.url 所在目录拼 canvas。源码位于 src/skills 时正确；Vite 合并为 dist/index.js 后变成 dist/canvas。复制脚本实际写入 dist/skills/canvas。recipe-catalog 在模块顶层同步扫描目录，异常先于子命令分发，无法靠 skills 的降级捕获恢复。

已对现有构建产物执行只读 `node packages/mcp-server/dist/index.js exec --dry-run`，直接得到 `ENOENT ... dist/canvas/references`；未连 daemon，未执行画布操作。

建议：明确源码目录和发布目录的定位契约，配方和 skills 消费同一发布根；构建门禁增加产物级离线启动检查，不能仅校验源码 skills 链接。不要通过复制两份目录掩盖路径分裂。

### P1：在途请求数量不能作为实例池槽位

位置：`src/daemon/run.ts:120`、`src/daemon/run.ts:244`、`src/daemon/server-pool.ts:62`。

A 进入拿实例 0；B 进入拿实例 1；A 先结束，inflight 降为 1；C 进入后 inflight=2，再拿实例 1，与仍运行的 B 冲突。无需超过默认池大小即可复现；异步工厂读取共享 inflight 还会进一步扩大错配可能。

对现有池函数按上述序列执行纯内存身份探测，B 与 C 返回同一对象。HTTP 层尚未做并发实机验收。可能重现 SDK ALREADY_CONNECTED / 500。

建议：每个请求领取空闲实例，并在该请求结束时释放同一租约；池满排队或明确拒绝，不复用忙碌实例。保留现有小池，不引入新的调度框架。

### P1：多节点导出到同一个 savePath，前面的文件被覆盖

位置：`src/tools/raw.ts:87`。

export 接受 ids 数组，循环内却对每项都 writeFileSync(savePath, bytes)，并为每项返回同一路径。ids 超过一个且传 savePath 时，最后一个文件覆盖之前内容；回包仍显示多个导出结果。

此项为代码审查确认，未执行文件覆盖实验。建议多项导出使用目录与唯一文件名，或写入前明确拒绝多 ids + 单文件 savePath；不得静默覆盖。

### P2：配方“扫描注册”与固定 ORDER 清单仍是两套事实

位置：`src/tools/recipe-catalog.ts:153`、`src/tools/prompts.ts:136`、`src/tools/prompts.ts:151`。

RECIPES 扫描全部 md，registerPrompts 却仅 ORDER.map。新增 md 会进入资源索引与补全，不会进入 prompts；删除 ORDER 中的文件会让注册抛错。当前 11 个 id 对齐，因此现有条目不是重复注册，而是扩展时会漂移。

建议：扫描结果决定全集，ORDER 只决定优先展示次序，未列出的条目稳定追加；参数 schema 中未知或遗漏条目在发布前校验。

### P2：目录预算把字符串长度当作 UTF-8 字节

位置：`src/daemon/catalog-proxy.ts:165`，同类口径在 catalog-budget 测试中。

真实 SDK 两跳目录探测：投影后的工具数组 JSON 为 378,917 个 JS 字符、443,575 UTF-8 字节。相差 64,658 字节，实际体积约高 17.1%。当前仍未超过 500,000 字节预算，但增长到边界时会漏报。原始目录约 1,457,494 字节，输入 schema 合计约 250,426 字节。

建议预算统一 Buffer.byteLength(..., 'utf8')，同时统计最终下发目录；输入字段与重复长描述按贡献排序优化，不能只看工具数量。SDK 两跳探测未附加宿主可能自行重复注入的 instructions 文本。

### P2：platform_op 的破坏性注解小于实际操作集合

位置：`src/tools/platform.ts:39`；删除入口见 `packages/ui/src/code/figma/ops.ts` 与 `packages/ui/src/code/mastergo/ops.ts`。

统一工具声明 destructiveHint=false，但可派发 figma_variables_remove、mg_variables_remove、mg_delete_component_property、mg_delete_variant_property 等删除动作。依赖注解判断写入性质的客户端会得到不完整分类。当前 idempotentHint=false，不存在由这条注解直接造成的代理自动重放。

建议聚合工具按最强副作用保守声明；只有确有客户端体验需求时，再分离只读平台查询与写入通道，不为每个 op 无差别新增 MCP 工具。

## 已纠正的上一轮遗漏

上一轮精简附录时删除了 title/when/args/role frontmatter。当时只验证了 skill 格式和链接，没有覆盖已改为扫描附录的 recipe-catalog。导入源码复现 `references/auto-layout.md 的 frontmatter 缺 when`。

本轮已恢复 11 篇附录的注册元数据，并把 when 描述收敛为任务触发条件。正文仍保留优化结果。通过 SDK 确认源码可注册 58 个工具及 11 个 prompts，HTML 参数能保留到渲染结果。此修复没有修改或重建 dist；发布路径问题仍待处理。

附带一致性债务：prompt-tools 直接 registerTool，不经过 bridgeTool；所以这两个工具不进入 executor map，jsd_batch 无法调用。若产品要求所有 jsd 工具都可编排，应统一登记流程；若仅供宿主读取，可明确作为例外。现有证据不足以要求删除该兼容入口。

## 候选与排除

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 保持简单：明确目录根、一次元数据、现有注册函数、空闲槽位租约 | 建议 | 问题在事实源与生命周期，无需增加模式层 |
| 重建工具注册框架或通用插件系统 | 排除 | 当前固定目录已能装配；新框架不解决路径、覆盖写或槽位身份 |
| 将所有任务收回单个通用 dispatch 工具 | 排除 | 掩盖参数类型与风险，增加模型猜 op 成本；已有专责工具可复用 |
| 删除所有协议兼容入口 | 排除 | prompts/resources/skills 及 proxy 面向不同客户端能力，不是同一层的重复注册 |

## 结论与实施顺序

不引入新模式。本记录为评审提议，除补回本轮发现的附录元数据遗漏外，没有实施运行时代码修改。

1. 先修发布资源定位，再由用户 build、重启 daemon，确认新进程能启动。
2. 修实例池请求租约与多项导出文件语义，避免连接冲突和覆盖文件。
3. 收敛配方全集与顺序，校正预算和破坏性注解。
4. 在兼容性核查后收窄两个 manage 入口；保留专责工具、batch 与必要的协议适配。

## 聚合入口收窄的具体方案

2026-11-01 补充审查：19 个 op 全部有专责入口；对照 schema 字段并集，没有聚合入口独有字段。仓内未发现通过 MCP 客户端直接调用旧名称的生产逻辑，实际执行路径由专责工具委托 node_op/component_op。外部客户端及用户保存的 callsFile 不在仓内搜索范围内，不能据此声称没有旧调用。

建议分成“迁移引用”和“移除公开入口”两步，在一次兼容性变更中交付；本轮仅形成方案，不执行删除。目标是只保留 56 个公开工具，不新增通用 dispatch 或默认启用的隐藏别名层。

### 第一步：先清除对旧入口的引导

- README 的两行工具目录及“聚合用于批量/混合”的说法，统一为“单操作走专责工具，多工具流程走 jsd_batch”。聚合 schema 单次只有一个 op，原说法没有独有执行能力支撑。
- 中英文 mcp.instructions、batch 描述及其他活跃描述中的旧名称，改为专责工具。历史 CHANGELOG 与旧决策正文保留。
- shared/core 的可执行错误提示须同步迁移：buildNode 中 reparent 提示、component 中 repair/copy_overrides 提示；execute-schemas 的 children 提示同样更新。否则删除入口后仍会引导用户调用不存在工具。
- 旧保存清单按上述迁移表转换；仅搜索仓内无法替用户证明外部清单已迁移。

### 第二步：移除 MCP 聚合注册

- tools/index.ts 移除 registerManageTools 的 import 与 registrar；tools/manage.ts 无调用后删除。
- 保留 tools/nodes.ts、tools/components.ts 的固定 op → node_op/component_op 适配，保留 jsd_batch。
- 保留 shared 的 manageNodesSchema/manageComponentsSchema、NodeOpParams/ComponentOpParams 和结果 schema；这些仍是插件协议及专责工具使用的内部契约。不要按 manage 前缀一并删除。
- 漂移复核仍走专责工具的 structural tag 与同一 hook，不搬进 batch，不直接绕过 executor 调 bridge。
- 更新 drift-hook 中依赖旧工具登记的用例，以专责工具单调和 batch 内调用覆盖同样的结构操作；旧名称仅在迁移说明和历史文件中保留。由用户运行测试。

### 必须同时处理的 hook 身份缺口

registry 在 payload(args) 注入固定 op 之前执行 hook.before(args)。专责 reparent 的原始 args 没有 op，但 DriftWatch.isReparentArgs 只认 args.op === 'reparent'，因此无法按该分支额外记录目标父层。

迁移时将固定 op 通过 hook 工厂闭包传给 DriftWatch，例如由 nodes.opTool 为结构操作创建绑定 op 的工厂。op 属工具定义的已知事实，不应为了 hook 要求用户继续传公开 op 字段，也不应通过“存在 parentId”猜操作身份。保留 checkDrift=false 的逐调用语义。

### 兼容边界

从 tools/list 移除并不自动保留 tools/call 兼容；直接取消注册后，旧名字的直接调用和旧 batch 清单都会失败。代理仅过滤展示也不是完整移除，上游仍暴露旧入口，后续同步也可能重新出现。

本方案默认在发布说明明确列出兼容性变更及 19 项映射。如果实际发现必须继续支持的外部旧调用，再选择有退出期限的兼容发布：直接调用兼容需要保留显式注册；仅旧 callsFile 兼容可在 batch 解析边界定向规范化后委托专责 executor。两者是不同承诺，不把仅支持 batch 宣称为保留全部旧 API。无证据时不提前加入环境开关或长期别名框架。

### 验收门槛

- tools/list 恰为 56 个唯一名称，旧两个名称与 executor 不再登记，19 个专责工具及 batch 都在。
- 迁移清单按专责 schema 校验；步骤 id、占位符、源/目标节点身份及破坏性语义保持明确。
- 结构操作的单调用和 batch 调用均保留漂移复核，reparent 覆盖旧父层、目标父层；checkDrift=false 可关闭。
- 活跃操作指引不再推荐旧名称；历史记录与迁移表允许保留。
- 类型检查由实现者完成；测试、build 由用户执行。若更新 shared，重载对应平台插件；mcp-server 构建后还需重启 daemon。当前另有发布目录路径故障，应先修复再做产物联调。

## 成本与退出条件

- 成本：目录定位需覆盖源码/发布两种运行形态；实例租约需保证断连也释放；弃用旧入口需迁移旧清单和文档。
- 精简工具后保留旧调用的迁移路径，不直接改变 node_op/component_op 插件协议。
- 若没有旧 manage 调用，可直接移除模型目录入口；若宿主已能访问 prompts，工具型 fallback 是否隐藏仍需客户端能力或使用数据支持。
- 若 SDK 原生提供满足连接模型的池，替换本地调度即可；业务工具定义与配方源不必随之改写。

## 验证

- 已做：源码配方导入；58 工具名称去重；11 prompts 与参数渲染；真实 SDK 内存连接的 daemon→proxy→客户端目录读取与 UTF-8 体积统计；实例池对象身份序列；现有构建产物的离线 CLI 启动探测。
- 未做：测试套件、lint、build、HTTP 并发实机验证、设计客户端写入、daemon 重启。
- 在线 jsd_ping 返回“上游重连超时(20000ms)”，当前客户端连接验收未完成；不据此单独断定所有在线故障都由同一原因造成。
- 后续验证：发布产物启动、不同完成顺序的并发请求、池满与取消、两项导出路径唯一性、扫描新增/删除配方一致性。遵守仓库约定，由用户运行测试与构建。
