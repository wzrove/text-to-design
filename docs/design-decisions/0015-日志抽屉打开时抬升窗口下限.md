# 0015. 日志抽屉打开时抬升窗口下限

- **日期：** 2026-09-21
- **状态：** 已采纳（已落地）
- **影响范围：** `shared/`（`panel.ts` 新增 `PANEL_HEIGHT_LOG`）、`ui/`（`components/PanelHeightSync.tsx`、`components/LogDrawer.tsx`、`App.tsx`）
- **相关记录：** 修订 0014（其「抽屉不参与高度决策」一条被本记录部分撤回）；「不为一处需求引依赖」取自 0012；不改 0001/0004 写入管线

## 压力

实测反馈：**打开日志面板，高度没有变高，矮搓搓的**。根因是两条各自正确的规则叠在一起：

1. 自适应布局下窗口高度 = 内容高度（`clamp(300, 640)`）—— 0014 的主结论；
2. 抽屉高度 = 窗口的 85% —— 0014 上一轮为消灭「开合抽屉把窗口顶一下」而定的比例。

于是抽屉的可用高度由**无关内容**的多少决定：连接提示是单行形态、能力表收起、未选中节点时，面板内容可以短到下限 300，抽屉就只有 255px；再扣掉它自己的标题行与过滤行（约 64px），日志区只剩约 190px ≈ 六行。日志是「要翻的列表」，不是「瞥一眼的浮层」—— 把它的高度挂在别处内容的多少上，是把 0014 那条妥协的代价转移给了最需要空间的地方。

同时要说清 0014 当初反对「抬下限」的理由还剩多少：它担心的是**抖动**。而开合抽屉是用户显式的一次动作，只在动作时变一次；面板宽度固定 360，不存在「窗口变 → 宽度变 → 中文重排 → 内容变高」那条回环（0014 压力 3 的机制）。所以那条理由在此处不成立，剩下的只是「开合时窗口跳一下」这个观感成本 —— 与「日志基本没法用」相比，这个成本可接受。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 打开期间把窗口高度下限抬到 `PANEL_HEIGHT_DEFAULT`（520） | 采用 | — |
| 维持现状（抽屉恒为窗口的 85%） | 排除 | 面板内容可短到 300，抽屉 255px，日志区不足十行 —— 本次反馈的现状 |
| 抽屉写死 `min-h`（如 420px）而窗口不变 | 排除 | 抽屉 `fixed` 定位于视口，比视口高时顶部被裁 —— 而关闭钮正在抽屉顶部，等于把出口裁掉；改成底部可达又要动抽屉布局，成本高于抬窗口 |
| 日志由浮层改常驻区块（进流，随内容撑高窗口） | 排除 | 与「诊断不进主视线」冲突：常驻区块要么长期吃掉剩余高度、要么把窗口永久顶高；且丢掉模态语义（遮罩、ESC、焦点回收到触发钮）会一并丢掉 |
| 给窗口尺寸加过渡动画 | 排除 | 宿主窗口尺寸不可动画；且为观感引依赖，命中 0012/0014 同一条纪律 |
| 把「日志开着」报给 code 侧、由 code 侧决定下限 | 排除 | 那是纯 UI 布局状态，送过去没有第二个消费方；契约两端保持「只认 height」更窄 |

## 结论

**不引入新机制，只给 `PanelHeightSync` 加一个 UI 侧的下限入参 `floor`**：请求高度取
`clamp(max(内容高度, floor))`，`floor` 在日志抽屉打开期间为 `PANEL_HEIGHT_LOG`（＝历史默认高度 520），关闭时为 0。

抽屉保持 `fixed` + 窗口 85% 不变；code 侧契约不变（仍只认 `height`，两侧各夹一次的口径也不变）。
「不体现在流里的高度需求」由此有了唯一入口，将来再有同类浮层（如新的诊断面板）直接复用这个入参，不必再改契约。

## 最小落地

- 角色与职责：`panel.ts` = `PANEL_HEIGHT_LOG` 取值真源；`App.tsx` = 唯一决定「何时抬」的地方（读 `logOpen`）；`PanelHeightSync` = 把 floor 与测量结果合并后发消息；`LogDrawer` = 只管取窗口的 85%，不关心窗口多高。
- 接口所在层与依赖方向：`floor` 只在 UI 内部传递，不进 `UiResizeMessage` —— code 侧看不到「日志开着没有」，它与面板尺寸契约无关。
- 一次开合的时序：点日志钮 → `logOpen` 变 → `PanelHeightSync` 的 effect 因读到 `floor()` 而重跑 → 重建 observer 并立即 `push()`（`sent` 复位，保证一定发出）→ `clamp(max(内容, 520))` → `ui_resize` → 窗口抬高 → 抽屉的 85% 随之变高。关闭走同一条路，floor 归 0、窗口回落。
- 关键实现点：`floor()` 必须在 effect **顶部**读一次（而不是只在 `push` 里读），否则它不是本 effect 的依赖 —— 抽屉是 `fixed`，内容高度不变、`ResizeObserver` 不会响，窗口也就不会抬。这是「打开没反应」的唯一可能成因。

## 成本与退出条件

- 成本：`PanelHeightSync` 多一个入参、`App.tsx` 多一行；开合时窗口跳一次（用户显式动作，且只在动作时发生）；floor 变化会重建一次 `ResizeObserver`（两态，可忽略）。
- 退出条件：① 若宿主改版后不再执行 `ui.resize`，floor 自然失效 —— 行为与改前一致，不更差；② 若未来宿主支持 auto 尺寸，整条测量链路（含本 floor）一起删；③ 若将来日志改为常驻区块（即在流内），本记录的 floor 由内容自身承担，应当删除。

## 验证

- 不变量测试：`pnpm run typecheck`（三包）、`pnpm run test`（87 用例）全绿；`tests/engine-api-compat.test.ts` 覆盖新增 UI 源码没有引入宿主缺失的现代 API。
- 引擎实测（2026-09-21，**已回填**）：三条全部确认 —— ① 打开日志后窗口抬到 ≥520（抽屉实测约 442 高，日志区可翻；此前 255px 的观感问题消失）；② 关闭后窗口回落到内容高度；③ 面板内容本来就高于 520 时打开日志**不会**把窗口压矮（`max` 生效）。未发现宿主对下沿的额外夹取或锚点偏移，故无需登记到 `.agents/skills/mcp-tdd/references/platform-limits.md`。
- 指标与日志：不新增日志。改尺寸失败仍只打 `console.error`（同 0014：面板尺寸是 UI 装饰，不是文档事实）。
