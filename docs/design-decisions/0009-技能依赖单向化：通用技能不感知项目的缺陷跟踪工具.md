# 0009. 技能依赖单向化：通用技能不感知项目的缺陷跟踪工具

- **日期：** 2026-09-19
- **状态：** 已采纳
- **影响范围：** `.agents/skills/software-design-patterns/`（SKILL.md、`references/{decision-log,output-template}.md`）、`.agents/skills/mcp-tdd/`（SKILL.md、`references/bookkeeping.md`）、`AGENTS.md`、`tests/skill-doc-budget.test.ts`
- **相关记录：** 0005（事实一致性用 Vitest 不变式测试守，不引入事件类架构）——本记录沿用同一条判据：能被机器守住的约束不靠文档纪律；0008（归档从人维护的文档改为台账自管）——同一次整理中发现的同一类「同一事实手写多份」问题

## 压力

`software-design-patterns` 里长着 4 处指向 `mcp-tdd` 的依赖，把两个技能焊成了双向：

| 位置 | 内容 |
|---|---|
| SKILL.md 工作流第 1 步 | 「本仓库有 MCP 报错台账时，`node .agents/skills/mcp-tdd/scripts/mcp-tdd.mjs list --json` 看有没有 `regressed` 指纹…」 |
| SKILL.md「与 mcp-tdd 的接口」整节 | 入口 / 出口 / 证据 / 回退 四行约定，明确写出 `handle … --decision NNNN` |
| `references/decision-log.md` | 「`.agents/skills/mcp-tdd` 的台账会自动按同一顺序查找编号，`handle --decision <NNNN>` 即可…」 |
| `references/output-template.md` | 「本仓库里就是 mcp-tdd 台账的 用例 id + 报错指纹 + 回归 runId」 |

代价具体在两个地方：

1. **复用性归零**。这个技能本身是**可移植**的：一套 GoF / 企业 / DDD / 分布式模式库，加一套
   「决策日志放哪、怎么编号、怎么取代」的通用机制，它按 `docs/design-decisions` → `docs/adr`
   → `docs/decisions` → `ADR` 的顺序**运行时发现**日志位置，本来就没绑定任何项目。
   一旦开始引用某个仓库的缺陷跟踪工具，它就从「通用技能」退化成「本仓的一个零件」，
   拷到别的仓库会带着一串断链。
2. **同一份约定被抄了两遍**。交接契约（什么时候转、编号怎么用、证据怎么回填、退出条件怎么回退）
   在 sdp 里写一份、在 mcp-tdd 的闸门段里又写一份 —— 这正是 0003 / 0007 反复消灭的
   「同一事实手写多份必然漂移」。而且两份都不完整：sdp 那份不知道 CLI 的强制规则，
   mcp-tdd 那份不知道决策记录的编号与取代规则。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| **依赖单向化**：删掉 sdp 里全部 mcp-tdd 引用；交接契约由 mcp-tdd 单方面持有；依赖方向用测试守住 | 采用 | 判门槛是调用方的事（不同项目用报错台账、回归用例、事故复盘还是评审意见，通用技能不关心）；把契约收到唯一一个知道全貌的地方，也就消灭了第二份副本 |
| 保持双向（两个技能互相写清对方） | 排除 | 就是现状的代价：复用性归零 + 契约两份。而且「互相知道」意味着改任何一边都要同步另一边 |
| 反过来：让 mcp-tdd 不提 sdp，各自独立、靠人在中间串 | 排除 | 复发闸门会拒收缺少决策的二次闭环 —— 被拒的人必须能立刻找到该去哪儿出决策。升级路径不可发现比耦合更糟 |
| 抽第三个「契约」文件，两边都引用它 | 排除 | 命中 0005 的反面信号：为一条边界新增一层共享文档。契约只有两个参与者，放到调用方那侧就够了；再加一层就又要维护第三份 |
| 把 mcp-tdd 的闸门逻辑整个搬进 sdp（让 sdp 判门槛） | 排除 | 方向反了。门槛依赖的是**报错闭环的语义**（指纹、回归 runId、复发），那是 mcp-tdd 的地盘；sdp 只负责「已确认的结构压力 → 决策」 |

## 结论

**不引入新机制，只切断一个方向的依赖，并把契约收敛到一处。**

1. **sdp 保持可移植**：`software-design-patterns/` 下不再出现任何 `mcp-tdd` / 台账 / 指纹的引用。
   - 工作流第 1 步的「再查现实」改成**与工具无关**的说法：项目若有失败信号源（报错台账、回归用例、
     线上告警、事故复盘 —— 是哪一种由项目决定），看有没有复发落在既有记录的「影响范围」内。
   - 「与 mcp-tdd 的接口」整节换成「**边界：本技能不判门槛**」：本技能只做「已确认的结构压力 → 决策」，
     什么算结构压力由调用方判定，产出固定为结论 + 候选排除 + 最小落地 + 成本与退出条件 + 编号 `NNNN`。
   - `decision-log.md` 只保留「位置定下就别搬家（编号会被外部引用）」，不再规定谁怎么回填。
   - `output-template.md` 的「验证」段改成：「具体形态随项目验证手段而定，唯一要求是别人能照着重跑一遍」。
2. **mcp-tdd 单方面持有交接契约**：新增 `references/bookkeeping.md` 的「转投设计决策」一节
   （判据表 / 命令序列 / 契约四点：编号规则、证据回填、退出条件回退、CLI 核对），
   SKILL.md 的闸门段只留判据表 + 一句走法 + 指向该节。
3. **方向由测试守住**（见下）。

## 最小落地

- **角色与职责**：`mcp-tdd` 是唯一同时知道「报错语义」与「决策记录在哪」的一侧 → 它判门槛、它回填；
  `software-design-patterns` 只知道「给一个压力，输出一个决策记录」，不感知追踪工具。
- **接口所在层与依赖方向**：`.agents/skills/mcp-tdd` → `.agents/skills/software-design-patterns`，
  **反向为零**。运行时耦合只有一个：sdp 按目录顺序发现决策日志，mcp-tdd 的 `handle` 按**同一顺序**
  查 `--decision NNNN` 的记录文件（这个顺序写在 `mcp-tdd.mjs` 的 `DECISION_DIRS` 里，也写进契约）。
- **创建与装配位置**：无新增文件。契约落在既有的 `references/bookkeeping.md`（它本来就是通道表），
  避免为一条边界新开一份文档。
- **一次调用的时序**：闭环第 4 步判「单点 / 结构」→ 结构型则 `python3 $D/scripts/new_decision.py "<标题>"`
  落 `NNNN` → 按记录的「最小落地」改（闭环 5–7 步）→ `handle --decision NNNN --verified-by <回归runId>`
  → `list --decision NNNN` 反查。

## 成本与退出条件

- 成本：sdp 少了一段「去哪儿找复发证据」的具体命令 —— 通用技能本来也不该给；mcp-tdd 的
  `references/bookkeeping.md` 多了约 1.4 KB 契约（该文件是按需加载的 reference，不在触发即读的体积里）；
  测试多两条断言（扫描 sdp 目录是纯读，毫秒级）。
- 退出条件：若本项目将来不再用台账闭环（改由 CI 回归用例或事故记录驱动），本记录的**机制**不变
  —— 只需把 mcp-tdd 侧契约里的「用例 id + 指纹 + 回归 runId」换成新的证据形态，sdp 侧仍是零改动。
  这条正是切断反向依赖的好处：换追踪工具只动一侧。

## 验证

- 不变量测试（`tests/skill-doc-budget.test.ts`，共 9 条全绿）：
  - **`software-design-patterns` 不引用 mcp-tdd（保持可移植）**：扫描该技能目录下所有 `.md`/`.py`/`.json`，
    命中 `mcp[-_]tdd` 即判红，报错信息带上文件名 + 行号 + 该行内容，并说明契约在 mcp-tdd 侧。
  - **反向的一半**：`mcp-tdd/SKILL.md` 必须出现 `software-design-patterns`（升级路径可发现），
    且 `mcp-tdd/references/bookkeeping.md` 必须出现它（契约落在那里）。否则复发闸门会变成拦路虎。
  - **反向实验已做**（验证守卫真的会咬人）：临时往 `output-template.md` 追加一行含 `mcp-tdd` 的注释
    → 该断言报红并指出 `output-template.md:47`；还原后恢复全绿。不会咬人的守卫等于没有守卫。
- 边界：sdp 的体积随删除的接口段从 9283 B 降到 **8831 B**（上限 10240 B），mcp-tdd 的 SKILL.md
  14246 B（上限 14336 B），两个 SKILL.md 合计 **23077 B**（上限 24576 B）—— 都在阈值内。
  注意 mcp-tdd 的余量只剩 90 B：继续往 SKILL.md 加内容会先撞它的单项上限，
  那时按仓库既有口径把清单移进 `references/`，不要调阈值。
- 指标与日志：无运行时指标；这是文档与技能边界的约束。
- 引擎侧实测：本轮**不涉及** `shared/` / `ui/`，无需 `pnpm build` 与重载插件；验证只到
  `pnpm run typecheck` + `pnpm run test`。
