# 0013. 错误链路：保持分层边界与载荷结构化及连接确认过期检测

- **日期：** 2026-09-20
- **状态：** 已采纳（已落地）
- **影响范围：** `shared/`（`dicts/error-code.ts`、`index.ts` 的 PluginResponse、`connection.ts`）、`ui/`（`code/plugin.ts`、`bridge/router.ts`、`bridge/connection.ts`）、`mcp-server/`（新增 `core/bridge-error.ts`、`pending.ts`、`bridge.ts`、`core/registry.ts`、`core/response.ts`）
- **相关记录：** 与 0007 同源（不允许静默失效，告警/错误须有出口）；依赖 0005（Vitest + CI 门禁）；不改 0001/0004 写入管线

## 压力

异步错误捕获横跨 4 层（进程入口 / MCP 工具 / 桥接 / 插件运行时），边界已经分层，但有三处真实成本：

1. **错误只有裸字符串，无类别**。`PluginResponse.error?: string` 承载不了分类，消费端只能猜：`daemon/proxy.ts` 的 `isTransportError` 对 message 做正则（`fetch failed|ECONNREFUSED|...`），措辞一变即静默失效，且无测试覆盖。
2. **同一错误被多层加前缀**。插件 `fail()` 拼 `${method} 失败:`，MCP 边界 `err()` 再拼 `错误:`，叠成 `错误: component_op swap_component 失败: in swapComponent: ...`；「下一步怎么办」散落各处。
3. **半开连接会「假在线」**。`ui/src/bridge/connection.ts` 的 `lastConfirmedAt` 只在 `onopen` 确认超时里用过，没有周期性过期检查：链路黑洞且无 `onclose` 时，面板永久停在 `connected` 却收不到任何推送。

变化频率低（台账 `regressed: 0`），但三处都是「判断被推给下游/靠猜」，失败后果是难定位的静默行为。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 保持分层边界，错误载荷结构化 + 单点格式化 | 采用 | 根因是数据模型（错误即字符串）与边界职责，不是缺结构 |
| Chain of Responsibility（统一错误处理链） | 排除 | 会把「谁吞了错误」变成间接问题（该模式自身列为常见误用）；现有边界短且顺序固定 |
| Retry | 排除 | Timeout 已全覆盖（`pending.ts` 超时、AbortSignal、重连预算 + single-flight），无未恢复/重试风暴证据 |
| Circuit Breaker + Bulkhead | 排除 | pending 有超时、reconnect 有预算与 single-flight，无资源耗尽信号 |
| Proxy（新增远程替身） | 排除 | `Bridge`/`PendingManager` 已是远程代理 + 超时/abort 边界 |
| Adapter 归一外部错误 | 暂不用 | 外部错误来源可在 throw 点直接附带 code，无需额外适配层；仅当未来上游 SDK 提供原生码时才局部引入 |

## 结论

**不引入模式，保持「边界捕获 → 中间层 reject 传播 → 顶层单点归一化」**，并把错误从裸字符串升级为带类别的结构化载荷。三件套：

- **载荷结构化**：`PluginResponse.error` 改为 `{ code: ErrorCode; message: string }`，`ErrorCode` 字典在 `shared/src/dicts/error-code.ts`（跨侧唯一真源）。不保留字符串兼容。
- **单点格式化**：daemon 侧新增 `BridgeError(code, message)`；`core/response.ts` 的 `err()` 从 code 决定前缀与 `followUp`，插件/传输层不再拼前缀。
- **连接确认过期检测**：`shared/connection.ts` 新增 `CONFIRM_STALE_MS = 2 * HEARTBEAT_MS` 与纯函数 `isConfirmExpired`；`ConnectionManager` 在 `connected` 期间用看门狗检测过期并主动关闭，交给既有 Scanner 重连。

## 最小落地

- 角色与职责：`ErrorCode`/`PluginError` = 跨侧取值；`BridgeError` = daemon 内部带类别错误；`ERROR_FOLLOW_UP`（response.ts）= 错误类别 → 下一步引导的唯一真源（单侧展示文案，不进 shared dicts）。
- 接口所在层与依赖方向：协议类型在 `shared`；`err()` 只在 MCP 边界；UI/插件只产生 code，不产出展示前缀。
- 创建与装配位置：`plugin.ts` 的 `send`/`fail` 生产 `PluginError`；`pending.ts` 把线上错误转为 `BridgeError`；`bridge.ts`/`registry.ts` 产出 `not_connected`/`platform_unsupported`/`invalid_args`。
- 一次请求/消息的调用时序：MCP 工具 → `bridge.request` → `pending`（超时/取消→`BridgeError`）→ WS → UI `router`（转发超时→`forward_timeout`）→ 插件（引擎错误→`engine_error`）→ 原路回包 → `pending` 转 `BridgeError` → `registry` catch → `err()` 单点格式化 → MCP 客户端。

## 成本与退出条件

- 成本：协议形状变更，需两侧重建 + 在即时设计重载插件；新增一个 UI 看门狗 interval。已取消字符串兼容以换取类型清晰。
- 退出条件：若上游 SDK/平台开始提供错误码，`ErrorCode` 优先映射原生码、删自造码；若实测半开从未发生，删看门狗只留 `onclose`。

## 验证

- 不变量测试：`packages/mcp-server/src/__tests__/error-codes.test.ts`（`err()` 统一 `错误: ` 前缀、code 决定 followUp、非 BridgeError 归 `plugin_error`）；`packages/shared/src/__tests__/connection.test.ts`（`CONFIRM_STALE_MS = 2 * HEARTBEAT_MS`、过期阈值边界）。
- 边界/并发/重试用例：现有 `pnpm run test`（80 用例）全绿；UI 转发超时 < daemon 超时的不变式保持不变。
- 指标与日志：`pending.ts` 失败响应日志带 `error=<code>`，可替代字符串正则做聚合；插件 console 仍保留堆栈与请求摘要。
- 引擎实测：重载插件后跑「未连接 / 引擎抛错 / UI 超时」三类失败用例确认文案不叠前缀。
