# 0022. 平台类型事实收敛为声明表，值域与适用性判定归位到-core-写路径

- **日期：** 2026-09-24
- **状态：** 已采纳（代码已落地并通过类型检查/不变式测试/三平台构建；**MasterGo 真机已逐条复验 A 类事实**，2026-09-24；Figma / jsDesign 真机复验待插件重载）
- **影响范围：** `shared/`（新增 `dicts/platform-value-domain.ts`、`core/runtime.ts` 加 `platform`、`core/props/` 写入判定、`schemas/base.ts`、`schemas/shared-props.ts`、`core/normalize.ts`）、`ui/`（三侧 `sync-guarantee.ts`、`code/mastergo/node-facade.ts`、`code/plugin.ts`）、`.agents/skills/mcp-tdd/references/platform-limits.md`
- **相关记录：** 沿 0002（运行时上下文显式注入）、0004（固定顺序 Pipeline 不短路）、0007（静默失效出口统一到 WriteOutcome）、0021（按平台类型逐项核对后不引入能力位）的做法，不取代任何记录

## 压力

三平台「属性值能不能被本平台表达」这件事，目前由**三份手写事实**分别兜，互相不知道对方：

1. **schema 枚举按 Figma 形态写**（`schemas/shared-props.ts`、`schemas/base.ts`）—— 是全平台超集；
2. **core 写路径**（`core/props/writers.ts`）只做 `'in' in node` 存在性守卫，不看值域；
3. **MasterGo 门面**（`ui/src/code/mastergo/node-facade.ts`）自己维护 `VALUE_TO_MG` 值映射与一处值域判定。

已产生的成本（可观察，不是"未来可能"）：

- **值域判定只落 console，对模型完全不可见。** `node-facade.ts` 的 `warnUnsupported`（`layoutAlign` 在 MG 只有 `STRETCH | INHERIT`，契约枚举却有 5 值）只打插件 console 的开发者日志 —— 调用方拿到的是「成功」，画布没变，**没有任何 warnings**。这与 0007「不允许静默失效」直接冲突，且是全仓唯一一处绕开该出口的落点。
- **jsDesign 缺 `PASS_THROUGH` 无任何判定。** `blendModeSchema` 有 17 值，jsDesign typings 的 `BlendMode` 只有 16 值（`J:546-562`，无 `PASS_THROUGH`）。写进去没人拦，也没有警告。
- **同一条类型约束按字段名逐点补，必然补不齐。** MG 的 `SolidPaint.color` 是 `RGBA`（`M:2220`，`a` 必填，注释明确「纯色模式下 alpha 始终为 1，请设置 color 中的 alpha」），于是门面有 `writeColor()` 折 alpha。但它只在 **2 个落点**被调用（SOLID paint、gradientStops），**漏在 effect 的 `color` 与 layoutGrid 的 `color`** —— 那两个字段的线格式也是 `rgbaSchema`，`a` 可以缺省。同一个类型事实按字段名补，补到第二处就开始漏。
- **必填字段的默认值写死在门面里，没有编译期断言守着。** `writeEffects` 按 MG 模型补 `spread` / `blendMode` / `showShadowBehindNode` / `gradient`（`M:2130-2149` 全部必填），`writeLayoutGrids` 手写字段清单。MG 哪天改了必填集合，没有任何东西会红。
- **适用性表是平台无关的，但事实是分平台的。** MG 的 `EllipseNode extends DefaultShapeMixin, ConstraintMixin`（`M:2793-2797`）**不含 `CornerMixin`** —— 椭圆上没有 `cornerRadius` / `cornerSmooth`；而 `PROP_APPLICABILITY.cornerRadius` 与 `cornerSmoothing` 都把 `ELLIPSE` 列在内。更糟的是门面的 `has` 陷阱做了「读得到就算存在」的兜底（`node-facade.ts:782-792`），`radiusWriter` 的 `if (!('cornerRadius' in node)) return;` 在 MG 椭圆上**拦不住**，值被写进一个不存在的字段。
- **事实台账在自己复制自己。** `references/platform-limits.md` 出现 3 组重复行（「组件/实例读不到 children」×2、「symbol sublayer」×2、「实例侧 componentProperties」×3），体积 19.1 / 20 KB 触顶。

变化频率：第三个平台（MG）刚接入（0017），其差异项**首次联调未做**，`platform-limits.md` 里 MG 相关行还在「撞一个补一个」地长。失败后果是静默的（回显成功、画布没变、无提示），靠人肉对照 typings 才能发现 —— 这正是上面第 3、4 条记录的成本。

## 候选与排除

| 候选 | 结论 | 排除理由 |
|---|---|---|
| 扩展既有机制：**dict 唯一真源 + 编译期断言**（新增按平台声明的值域/适用性表，判定归位到 core 写路径） | 采用 | — |
| Adapter / Facade（把投影做完整） | 部分采用，不作主结论 | 已在位（三 adapter + MG 门面）。压力不在「接口不兼容」，而在**值级投影不完整**与**判定层缺位**；把值域判定继续留在门面里，就还是在平台层做策略，违背架构约定的分层 |
| Chain of Responsibility（连续规则可短路） | 排除 | 0004 已明确本仓写后校验是**固定顺序且必须全部执行、不短路**的 Pipeline；责任链的价值（可短路、调用方不知道谁处理）在这里都不成立 |
| Bridge / Abstract Factory（把「平台」与「属性」两个维度拆开） | 排除 | 平台维度已是三份 adapter、属性维度已是 PropWriter 表（0001）；再拆一层只会把两个已经有了的变化轴变成三个 |
| 保持简单：继续在门面里 `console.warn` | 排除 | 命中停止条件「根因是职责划分或数据模型错误」——真正缺的是**判定的位置**（该在 core，因为只有 core 手上有 `ctx` 与 `outcome`）与**事实的载体**（两处手写必然漂移）。继续 console 就继续违反 0007 |

## 结论

**不引入新模式。** 沿仓库既有两件工具把事实收口：

1. **事实收敛到一份按平台声明的表**（`shared/src/dicts/platform-value-domain.ts`，唯一真源）：只登记**比线格式更窄**的项 —— ① 值域收窄（jsDesign 的 `blendMode` 除 `PASS_THROUGH`；MG 的 `layoutAlign` / `layoutGrow`）；② 按节点类型的适用性收窄（MG 的 `cornerRadius` / `cornerSmoothing` 除 `ELLIPSE`）。**不收「三平台一致」的项** —— 那部分线格式与 typings 已经同形，收进来只是把事实抄第二遍，还会把「该平台不支持」误报成「值不合法」。
2. **判定归位到 core 写路径**：判定需要 `RuntimeContext`（知道当前平台）与 `WriteOutcome`（出口），这两样**只有 core 有**。故 `RuntimeContext` 增加只读的 `platform`（仍是 0002 的构造期快照，不破坏「运行期只读」），值域/适用性被拒时进 `outcome.ignored` + `warnings`，走 0007 的统一出口。

门面侧只留**投影**：值域判定的**事实**改为从上面那张表导入（不再自己写一份 `ALIGN_SELF_SUPPORTED`），必填默认值集中成带 `satisfies` 断言的常量表，颜色统一走一个 `mgColor()` —— 任何流向 MG 的 RGBA 都从这里过。

**为什么这不是新模式**：dict + 编译期断言 + WriteOutcome 出口都是本仓既有的机制（0001/0004/0007/0021）；本记录只是把「平台类型事实」这一类数据也放进去，并纠正判定的归属层。正如 0021 的结论「逐平台类型核对后不引入能力位」，这次也不引入新能力位。

## 最小落地

- **角色与职责：**
  - `dicts/platform-value-domain.ts`：按平台声明值域收窄与适用性收窄 + `platformValueAllowed()` / `platformPropAppliesTo()` 两个纯查询。
  - `core/props/platform-gate.ts`：把上面两个查询 + `WriteOutcome` 写成一次判定 `gatePropWrite()`，返回是否放行与点名文案。
  - `core/props/types.ts`：新增 `writeProp(ctx, node, key, value)` = 判定 → `putIfPresent`，作为**唯一写入收口**（取代各 writer 直接调 `putIfPresent`）。
  - `ui/src/code/mastergo/node-facade.ts`：只做投影；`mgColor()` 统一补 `a`；`MG_EFFECT_DEFAULTS` / `MG_GRID_FIELDS` 常量表代替内联补丁。
- **接口所在层与依赖方向：** 表在 `shared/dicts`（无依赖），判定在 `shared/core/props`，断言在 `ui/src/code/*/sync-guarantee.ts`（唯一能 import 平台 typings 的层）。方向仍是 core → dicts；平台包 → core；**不反向**。
- **创建与装配位置：** `plugin.ts` 用 `meta.capabilities` 与新增的 `platform` 一起装配 `runtimeContext(...)`。
- **一次请求的调用时序：** MCP → daemon → plugin.ts `registerPlugin` 持有 ctx → `updateSelection(host, ctx, …)` / `executeOps(host, ctx, …)` → `runWriters` → 各 writer 调 `writeProp(ctx, …)` → 被拒项进 `outcome.ignored`/`warnings` → 结果装配期统一上行。

## 成本与退出条件

- **成本：** 新增 2 个文件 + 1 个 `RuntimeContext` 字段 + 约 15 处 `putIfPresent → writeProp` 的机械替换 + 三侧断言。没有新的间接层、状态机、网络跳数或存储。
- **退出条件：** 若某平台（如未来第四平台）在 typings 层面与线格式同形、不再有窄化项，则该平台的条目从表中删空，`platformValueAllowed()` 恒真 —— 判定退化为原来的存在性守卫，代码可整块删掉，不影响其它平台。若 `platform-limits.md` 中「类型系统事实」类条目归零，本记录即可标为已废弃。

## 验证

真机还暴露了一个**本记录范围外的既有缺口**（已修 + 单测钉住）：`layoutWriter.settle` 把对齐回读放在 `src.layoutMode == null` 之后，于是「只改对齐、不传 layoutMode」的路径**完全没有回读校验** —— MG 上丢掉对齐也照回「已更新 1 个节点」。台账指纹 `8a9623518bc5`。另：MG 上把对齐写成 `MAX`（映射 MG `FLEX_END`）回读恒为 `FLEX_START`，而同节点写 `CENTER` 能落盘 → 疑引擎不接受 `FLEX_END`，**未定论**，指纹 `8841b29b8ad1`。

> 追加（同日，**已定论**）：`FLEX_END` 在 **typings 层面是合法的**（MG `mainAxisAlignItems`(index.d.ts:2594) / `crossAxisAlignItems`(2595) 取值域都含它），故映射没错 —— 逐值实测（FRAME + `flexMode=HORIZONTAL` + 两子节点，每次只写一个值再回读）确认：`MIN`/`CENTER` 生效，**`MAX`/`SPACE_BETWEEN` 被引擎静默忽略**（回读保留上一个生效值，不是归一化）。
> 因此它是**运行时事实**而非类型事实，收在新增的 `PLATFORM_RUNTIME_VALUE_DOMAIN`（断言方向与类型事实表**相反**：登记项必须**在** typings 里，否则该登记本就属于类型表）—— 这是本记录「A/B 两张表」原则的第一次落地。同批还堵了两个绕过判定的写入路径：创建分支的对齐直写、`settle` 回压会把被拒的值再写一遍。
> 仍未定论：`layoutGrids` 在**合法宿主（FRAME）**上也回读不到（台账 `ded745d7eea7`），已排除宿主类型因素。

> 追加（同日，`layoutGrids` **已定论 → 平台侧行为**）：逐平台核过宿主 mixin（三平台一致只在 frame 族）、也核过 MG 的字段名与值域（`gridType` / `LEFT|RIGHT` / 带 `a` 的 RGBA），门面映射**没问题**。真机逐帧实测给出决定性证据：**同一份参数连写 8 帧只成 1 条**，而落地那条的值**完整正确**（`pattern`/`count`/`gutterSize`/`alignment`/`color` 逐项对得上，引擎另补默认 `sectionSize: 8`）；且**可见性同样不可靠**：落地那条同会话回读为空、数分钟后才读到，后续复验又出现「先能读到、之后同一 id 读不到」与「跨插件重载后消失」两种**反向**不一致。输入相同、代码确定 ⇒ 方差全在平台侧（**不能假定它稍后会稳定下来**，故文案不写成「写入失败」也不写「稍后即可」，而是要求画布目检）。故：
> - 平台的「偶发落地 + 回读滞后」进 `platform-limits.md` 的 B 类行（含工具面决策：不加 MG 网格 op —— `createGridStyle` 需要「已有网格的节点」当输入，节点级写不进去时它同样无从下手）；
> - **我们该修的是「静默」**：`paintWriter` 给 `layoutGrids` 补写后回读校验（`verifyLayoutGrids`），点名「请求 N 条 / 回读 M 条」并**区分**「写入未发生（存在性守卫跳过）」与「写入已发出但引擎未保留」—— 这两种成因从结果里观察完全相同，不区分就无从排查；MG 走专用口径，明说**不必然代表写失败**、以画布目检为准（写成「写入失败」会诱导无谓重试刷屏）。
> 两条指纹（`ded745d7eea7` / `8841b29b8ad1`）均已按 `product-bug` 闭环，回归 run `run-20260924T135615Z`；台账当前 **0 未决**。
> **MG 侧已用补齐后的参数复验（2026-09-24，MG 客户端）**：同一套参数、同一条写路径，在 jsDesign 上五种形态全通，在 MG 上**五种全部零落盘** ⇒ MG 的「读不到」**不是**参数问题（与 jsDesign 相反），是引擎不收节点级网格。故 MG **保留**在 `LAYOUT_GRID_UNVERIFIABLE_PLATFORMS`，早期那次「8 帧成 1 条」是**旧参数**时期的观测，已从文案与台账里撤下，避免诱导重试。

> 追加（同日，jsDesign 真机复验）：类型事实一侧通过 —— 写 `blendMode: 'PASS_THROUGH'` 被拒并点名（列出 16 个接受值），`MULTIPLY` 照常落盘无告警。**新发现一条运行时收窄，与 MG 同形**：jsDesign `LayoutMixin` 声明 `layoutAlign` 5 值、`layoutGrow: number`，但子项侧只认 `STRETCH`/`INHERIT` 与 `0|1`（父设交叉轴 `MAX`、子默认贴右 `x=150` 时写 `MIN` 毫无变化；写 `STRETCH` 立刻 `w` 40→180 ⇒ 写入路径是通的，是取值被吞）⇒ 收进 `JSDESIGN_RUNTIME_VALUE_DOMAIN`（与 MG 同一张运行时表，断言方向相反；变异测试证明断言非恒真）。**诚实标注**：`layoutGrow` 那条断言天然弱（jsDesign 把它写成 `number`，数值域收窄没有类型信号），属实测冻结，引擎放宽后手动删项。
> 后续**推翻**，见下方变更史末行：jsDesign 的 `layoutGrids` 读不到，根因不是平台不可验证，而是**我们的值不合法**（漏给 `sectionSize` / `offset`，引擎 `set_layoutGrids` 逐变体校验后整条拒绝，且此前静默）。归一化补齐后五种形态全部落盘并回读到值，jsDesign 已从 `LAYOUT_GRID_UNVERIFIABLE_PLATFORMS` 撤出。**教训**：可修的参数问题被记成「平台不可验证」会掩盖根因 —— 兜底口径必须有撤回路径与复验触发条件。
